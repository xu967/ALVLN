**这套代码做什么：** 单目 RGB 加短指令，输出四个离散动作（SAFE_NEUTRAL / FORWARD_SLOW / YAW_LEFT / YAW_RIGHT），
目标部署到 LicheePi + ESP32 微型四轴。训练推理自研 C++/CUDA，数据来自 Gazebo 和 3DGS 仿真，Studio 是桌面监控台。
**负载假设：** 一个人在一台 RTX 2080 Ti 服务器上跑采集、训练、评测；Studio 单用户。不考虑多用户并发。

## 0. 结论

1. 仿真里的无人机和你的真机不是一类东西。差的不只是外形，质量、尺寸、电机、飞控、高度保持、动作执行方式全都不同（§1）。
2. 重新仿真的办法：把 CF-Drone 固件的控制代码原样编进仿真（固件在环，SITL），机体参数用实测值，
   指令走真机将来用的同一条摇杆通道（§2）。CF-Drone 的上游 Flix 就是这样做模拟器的。
3. 「真实仿真环境」按 载具 → 传感器 → 场景 的顺序做。载具不对，场景再逼真，策略照样迁移失败（§3）。
4. 可视化里有 4 处会给出错数字或挂错实验（#5–#8），还有明显卡顿和布局问题（#9–#12）。
5. 动手前要你拍板 6 件事，最关键的是「高度和速度由谁来稳」（§6 D2、D3）。

## 1. 你的真机 vs 现在的仿真

机型按 `CF-Drone/control.ino:13`「参数适配118mm轴距」和 `sim/dynamics/cf_sil_v1.json` 的 `wheelbase_m: 0.118`
推断为 **琛光 E1 MINI**。官方规格页：ESP32，轴距约 118 mm，约 80 g（含标准电池）
（[E1 MINI 规格](https://docs.cherglowtech.com/e-series/e1-mini/specs)，2026-11-05 读取）。
如果你飞的是 E1 Nano（ESP32-S3，50 mm，约 25 g，[规格页](https://docs.cherglowtech.com/e-series/e1-nano/specs)），下表数值要换。

| 项 | 真机（E1 MINI + CF-Drone 固件） | 现在的仿真（Gazebo X3） |
| --- | --- | --- |
| 质量 | 约 80 g 含电池；挂 LicheePi、相机后未称 | 1.5 kg（`sim/worlds/uav_rgb.sdf:176`） |
| 尺寸 | 轴距约 118 mm，桨尖外径估计 0.18 m 左右（桨径未测） | 电机对角 0.51 m，桨尖外径约 0.71 m（转子半径 0.1 m） |
| 电机 | 有刷电机，MOSFET 直驱，25 kHz、10 bit 占空比（`CF-Drone/motors.ino:14-20`）；1S 锂电，推力随电压掉，固件不补偿 | 无刷、按转速给定的电机模型，推重比约 1.49（`uav_rgb.sdf:407-466`） |
| 飞控 | STAB 模式：杆量 × 30° 得目标倾角，偏航杆 × 300°/s（`control.ino:41-42, 160-167`）；角度环 P=6，角速率 PID 0.06/0.1/0.001，约 1 kHz | Gazebo `MulticopterVelocityControl`，直接用仿真真值跟踪机体速度；最大加速度 2 m/s²，相当于最多倾 11.5°（`uav_rgb.sdf:468-483`） |
| 姿态估计 | 飞行中只靠陀螺积分。加速度计只在落地静止时修正（`estimate.ino:54`），水平修正关闭（`:12, :30`），所以姿态会慢慢漂，松杆也会横向漂 | 真值，没有估计误差 |
| 高度 | **没有定高**。ALTHOLD 只是个常量（`control.ino:43`），油门开环映射到 0.10–0.90 占空比（`:157`） | 用真值 z 做 P 控制，稳在 2.1 m（`sim/tools/collect.py:100-138`） |
| 动作执行 | 固件只认摇杆量，没有四动作解析器（`docs/uart_action.md` §1） | 每步发机体速度：前进 0.3 m/s、偏航 0.6 rad/s；窗口结束立刻发零速刹停（`collect.py:97-119, 934`） |
| 松杆后 | 机体回水平，靠空气阻力滑行，不会停 | 主动刹停，原地不动 |
| 相机 | 型号、视场角、分辨率、延迟都未知，仓库和交接文档里没有任何一份给出 | 理想针孔，60°、320×240、30 Hz，装在机身前 0.2 m，无噪声、畸变、模糊、延迟（`uav_rgb.sdf:191-211`） |

直接后果：

- 学生现在学到的是 X3 的习惯：「前进 = 匀速走一段然后停住」「SAFE = 原地不动」。真机上前进是倾角加速、松杆滑行，SAFE 回中后还在漂。
- 证据：`docs/experiments/2026-11-04-cf-stab-dynamics.md:65-69`。同一个在 x3 数据上训练的学生，只把执行换成 cf_stab
  （倾角加速 + 滑行 + 0.15 s 延迟），SR 从 0.59（10/17）掉到 0.06（1/17）；GT 教师也从 0.94 掉到 0.65。
- 尺度：场景的 1.2 m 车道缝是按 X3 的 0.71 m 外径定的。换成约 0.18 m 的真机，可通过性、碰撞判定、相机离障碍物的距离全变。
- 余量：E1 MINI 约 80 g，挂上 LicheePi 和相机后悬停占空比未知；固件油门上限 0.90（`control.ino:48`），
  饱和时 `desaturate` 先保总推力、压缩姿态力矩（`:229-257`）。悬停占空比太高，姿态就控不住。上机前必须称重并测悬停占空比。

## 2. 怎么重新仿真

### 2.1 三条路比较

| 方案 | 做法 | 好处 | 问题 |
| --- | --- | --- | --- |
| **A. 固件在环 SITL（推荐）** | CF-Drone 的 `control.ino`、`estimate.ino`、`safety.ino`、`pid.h`、`lpf.h`、`vector.h`、`quaternion.h` 原样编进一个 C++ 库，外面套一层 Arduino 打桩 + 刚体/电机模型，按仿真时间 1 kHz 锁步 | 控制器和真机逐行一致；固件更新，仿真自动跟上 | 要写打桩和刚体模型；参数必须实测 |
| B. 继续调占位模型 | 再调 cf_stab / cf_sil / cf_blackbox | 不写新代码 | 三套互相矛盾，全是猜的（#15）；cf_sil 的控制线程只拿到约 50 Hz 位姿，和固件 1 kHz 不是一回事 |
| C. 直接用上游 Flix 模拟器 | [okalachev/flix `gazebo/`](https://github.com/okalachev/flix/tree/master/gazebo)：Gazebo 插件里直接编译固件代码，机体 65 g | 思路现成 | 基于 Gazebo Classic 11（README 推荐 Ubuntu 20.04，Classic 已停更），本机是 Gazebo Harmonic 8.15；它把估计的偏航直接改成真值（`simulator.cpp` 里 `attitude.setYaw(...)`），推力按占空比线性算；GitHub API 显示该仓库当前没有可识别的 LICENSE，复用代码前要确认授权 |

### 2.2 推荐做法（最小可用版）

- **一个库** `sim/cf_sitl/`（C++）：只做三件事，调用固件控制代码、积分电机、积分刚体。
  对外一个函数：输入摇杆量和步数，输出位姿、速度、姿态、电机占空比。
- **两个使用方**：
  - 3DGS 路线：Python 用 ctypes 调库，按相机帧率在库给出的位姿上渲染，直接替换 `sim/3dgs/dynamics.py → cf_blackbox`。
  - Gazebo 路线（柱阵、校园、接触传感器）：以后包一层 gz-sim8 System 插件调同一个库。
    本机 `/usr/lib/x86_64-linux-gnu/cmake/gz-sim8` 在，开发包齐。
- **一个桥**：`动作 → 摇杆量` 的映射只写一份 Python。仿真里喂给库；真机上原样编成 CRSF 帧，
  从 LicheePi 串口发到 ESP32 的遥控接收口（`CF-Drone/rc.ino:131-142`，420000 波特率 8N1）。固件不用改。
- **一份参数** `sim/dynamics/e1_mini.json`：字段全部来自 §2.3 的实测；没测的留 null，`calibrated=false`。
- 过了 §2.4 门禁后，删掉 cf_stab / cf_sil / cf_blackbox 和它们的测试，只留这一套。

不要做的：不要像 Flix 那样把偏航改成真值，那会抹掉真机的偏航漂移；不要在 SITL 里偷偷加定高或定速，真机没有，除非 §6 D2 决定加。

### 2.3 要在真机上测的参数（按优先级）

| 参数 | 怎么测 | 用在哪 |
| --- | --- | --- |
| 整机质量（含电池、LicheePi、相机、线） | 0.1 g 精度的秤 | 刚体、推重比 |
| 电机中心位置、桨径、机体外包络 | 卡尺 | 力矩臂、碰撞体 |
| 占空比 → 推力曲线（满电 / 半电 / 低电三档） | 飞机倒扣固定在秤上，占空比 0.1–0.9 扫一遍。固件现成的 `mfr/mfl/mrr/mrl` 只能固定 30%（`CF-Drone/motors.ino:74-82`）；扫占空比要用 MAVLink `SET_ACTUATOR_CONTROL_TARGET`，只在 AUTO 模式生效（`mavlink.ino:195-207`） | 电机模型 |
| 悬停占空比 | 飞一次后 CLI `log dump`，看 `thrustTarget` 列 | 校推力曲线、电池模型 |
| 打杆阶跃响应 | 同一份 `log dump`：rates、ratesTarget、attitude、attitudeTarget，100 Hz（`log.ino:21-36`） | SITL 验收的金标准 |
| 三轴转动惯量 | 双线摆，量摆动周期 | 刚体 |
| 电机时间常数 | 占空比阶跃，手机慢动作或麦克风测转速 | 电机模型 |
| 陀螺静置漂移 | 静置 60 s 记录 | 偏置模型，用来复现姿态漂 |
| 控制环实际频率 | CLI `time`，WiFi 开、关各一次 | SITL 步长 |
| 飞控里存的参数 | CLI `p` 全部导出（NVS 里的值会覆盖代码默认值，`parameters.ino:198-222`） | SITL 参数 |
| 相机内参和畸变、分辨率、帧率、曝光模式、端到端延迟、安装位置和俯仰角 | 棋盘格标定（本机 cv2 可用）；延迟用 LED 闪灯对拍 | 相机模型 |
| 线性阻力 | 松杆滑行，上方手机拍视频，地面贴刻度 | 刚体 |

固件日志只有 14 列，没有电机占空比、原始 IMU、电池电压。要做完整辨识，得在日志里加这三列（见 §6 D5）。

### 2.4 验收门禁

- G1：同一串打杆输入，SITL 的 rates / attitude 曲线和真机 `log dump` 对齐（误差阈值你定）。
- G2：SITL 悬停占空比和实测相差 ±5% 以内。
- G3：松杆滑行距离、前进打杆位移，和顶视视频对齐。
- G4：G1–G3 都过了才拿它采数据、训学生；数字单独成档，不和 x3 档混报。

## 3. 「真实仿真环境」怎么做

| 层 | 现在 | 要做到 | 依据 |
| --- | --- | --- | --- |
| 载具（动力学 + 飞控 + 指令接口） | X3 + 真值速度控制 | §2 的 SITL | cf_stab 实验：只改执行方式，SR 0.59 → 0.06 |
| 传感器（相机、IMU） | 理想针孔，无噪声无延迟 | 真相机标定参数，加一个 Gazebo 和 3DGS 共用的相机后处理（畸变、噪声、运动模糊、曝光、延迟队列） | 真相机参数一项都没有 |
| 场景（外观 + 几何） | 纯色方块柱阵、低模校园；3DGS pilot 用公开场景 | 用 3DGS 重建你真正要飞的场地 | [SOUS VIDE](https://arxiv.org/abs/2412.16346)：在高斯泼溅模拟器里训练的视觉策略零样本迁移到真机；[GRaD-Nav](https://arxiv.org/abs/2503.03984)：3DGS 加可微动力学训练视觉导航 |

另外两个现状要先知道：校园任务最近一次完整闭环是 0/80 成功（AUDIT #7）；3DGS 的「成功视频」是把目标点从 -6 挪到 -7.5 才成功的（AUDIT 已核实）。
所以现在先补外观收益不大。

3DGS 重建真实场地的流程（缺的步骤已标出）：

1. 拍摄：最好用真机的相机，锁曝光，在 1.5–2.5 m 高度绕场地拍视频，保证足够重叠；场地里放 ArUco 板或量好的卷尺距离，定尺度和重力方向。
2. SfM 求位姿：COLMAP 本机未装，`apt` 候选版本 3.9.1。根分区只剩 2.4 G，数据和中间结果放 `/root/rivermind-data`（剩 66 G）。
3. 训练：gsplat 1.5.3 已在 `$DATA_ROOT/3dgs-venv`；仓库里没有训练脚本，用 gsplat 官方 examples 里的 `simple_trainer.py`。
4. 尺度和重力对齐：求一个相似变换，一次性作用到 means、quats、scales，让 `nav_to_world` 保持单位阵。现在的转换器只转了 means（#4）。
5. 碰撞几何：现在的代理不可信（#3）。改成按不透明度筛过的 3D 占据，或用渲染深度做 TSDF 出网格（Open3D 未装）；沿轨迹扫掠检查。
6. 验证：留一部分真实照片不参与训练，同位姿渲染对比；真机和仿真飞同一条路线，对比轨迹。

## 4. 编号问题清单

### 必须修

1. **仿真载具不是你的飞机**（`sim/worlds/uav_rgb.sdf:170-487`、`sim/tools/collect.py:97-138, 934`）
   - 是什么：所有采集和闭环评测用的那架无人机，以及动作怎么执行。
   - 问题：1.5 kg 的 X3 用仿真真值做速度闭环和定高，每个动作窗口结束就刹停。真机约 80 g，只稳姿态，油门开环，松杆滑行（§1）。
   - 修：按 §2 做 SITL，参数实测。不要再调第四套占位模型。
   - 不修：仿真里的任何 SR 都说明不了真机能不能飞。

2. **部署链路的三条约束不能同时成立**（`docs/HANDOFF_3DGS_20261105.md:7-13`、`tools/uart_action.py`、`CF-Drone/rc.ino:131-183`、`CF-Drone/control.ino:43, 157`）
   - 是什么：LicheePi 怎么让 ESP32 执行四个动作，以及高度靠什么保持。
   - 问题：交接里定的是「UART 发动作 ID + ESP32 不改 + 固定 2 m」。固件里没有四动作解析器，`uart_action.py` 的占位帧接哪个口都不会被执行
     （接 USB 口会进 CLI，那里有 `arm` 和电机测试命令）；固件也没有定高。
   - 修：固件不改时，唯一能用的通道是 LicheePi 模拟 CRSF 接收机发摇杆帧；高度先在 §6 D2 选方案。`uart_action.py` 的占位协议先冻结。
   - 不修：上机时要么动作发了没人执行，要么能执行但高度没人管。

3. **3DGS 的碰撞代理不可信**（`sim/3dgs/collision.py:20-121`、`sim/3dgs/collect_3dgs.py:174`；AUDIT #2、#3）
   - 是什么：3DGS 场景里判断撞没撞的体素占据。
   - 问题：(a) 占据用原始 PLY 坐标建，渲染却用 `nav_to_world`（AUDIT #2）；(b) 只在每步终点查，终速下一步 0.69 m，能穿过膨胀后 0.6 m 宽的障碍（AUDIT #3）；
     (c) 只看 0.4 m 高薄片里的高斯中心，不看不透明度。Callinstrasse 薄片里 58% 的点不透明度低于 0.1，是看不见的幽灵墙，伸进薄片的大高斯反而漏掉；
     (d) 膨胀形状取决于装没装 scipy（`3dgs-venv` 有，`.venv-tools` 没有），两个环境结果不同。
   - 修：在导航坐标系里，用不透明度筛过的高斯建 3D 占据（或渲染深度做 TSDF 网格），沿轨迹扫掠检查，膨胀用固定的圆形结构元素。
   - 不修：3DGS 的碰撞率和 SR 没有意义，换真实场地后错得更明显。

4. **`splat_to_ply` 把场景转歪，还转成了镜像**（`tools/splat_to_ply.py:29-36`）
   - 是什么：把 .splat 场景转成本仓库用的 PLY。
   - 问题：只旋转了高斯中心，每个高斯的朝向四元数原样写回（:36）；加 `--flip-height` 后整体变换行列式是 -1，场景左右镜像。
     `bicycle_real` 就是这样转出来的：扁平的地面和叶片高斯变成竖片，深度跟着错。
   - 修：只允许正交旋转（行列式 +1），同一个旋转同时作用到 means 和 quats，scales 乘尺度；删掉 `--flip-height`。加一个测试：转换前后同位姿渲染一致。
   - 不修：用它导入的场景看着差不多，几何和碰撞是错的。

5. **Studio 把评测结果挂到别的实验上**（`ui/studio.py:2457`、`:1491`；AUDIT #5）
   - 是什么：异步闭环评测结束后，把结果写进 run 的摘要和报告。
   - 问题：写入的是「结束时界面上加载的 run」，不是「启动评测的 run」。`_auto_eval_note`（:1491）有同样问题，自动录像的备注也会写错 run。
   - 修：启动评测时记下 run 目录，归档和备注都用它。
   - 不修：权重、评测、视频对不上号，报告给出错误归因。

6. **首页的 Best Val Macro-F1 和验证曲线用的是截断数据**（`ui/studio.py:728, 1548`、`ui/monitor.py:37-38, 160`）
   - 是什么：Dashboard 首页的最佳验证 F1 卡片和验证曲线。
   - 问题：加载历史 run 时只读最后 1 MiB、最多 200 条事件，事件队列上限 300 条。
     实测 `l1-stop-500-173307/run-film-dec-ft` 有 30 条 val 事件，首页只剩 1 条；合成用例里卡片显示 0.600，保存的报告是 0.9。
   - 修：reset 时用 `read_jsonl()` 读全量非 train_step 事件（`summarize_run` 已经这么做），val 事件放无界列表。
   - 不修：首页数字和报告对不上，照首页挑权重会挑错。

### 应该修

7. **评测 `ckpt.bin` 会被判成「旧评测」并藏起来**（`ui/studio.py:404-420`）
   - 是什么：判断一份 eval.json 是不是当前 run 权重的评测。
   - 问题：不管报告评的是哪个文件，都拿 `ckpt_best.bin` 的哈希比，评末轮 `ckpt.bin` 的报告永远对不上。
   - 修：报告里有 ckpt 路径就算那个文件的哈希，没有才退回 `ckpt_best.bin`。
   - 不修：末轮权重的评测在 run 页面看不到。

8. **训练后自动跑的 1 集录像，被当成「闭环评测成功率」大卡**（`ui/studio.py:1467-1490, 1593-1623`）
   - 是什么：默认勾选的「训练后保存视频」会跑 `episodes=1` 的评测，结果目录放在 run 下面。
   - 问题：run 只有这一份评测时，首页大卡直接显示 1.000 或 0.000，只有副标题写着 episodes=1/1。
   - 修：自动录像目录加标记，`_run_eval_paths` 不收它；或者大卡改成「录像（1 集），不是 SR」。
   - 不修：一集的结果容易被截图当成功率汇报。

9. **仿真页卡顿：相机帧在主线程先编 PNG 再解 PNG**（`ui/studio.py:2016-2030`、`sim/tools/save_frame.py`）
   - 是什么：Studio 仿真页三路相机画面的显示。
   - 问题：每帧先用纯 Python 编成 PNG（chase 一帧 27.7 ms），再用 PIL 解码、LANCZOS 缩放，每帧还调 `update_idletasks()`。
     三路相机加地图，一次刷新中位 108.5 ms，超过 80 ms 的刷新周期。
   - 修：`Image.frombuffer(..., "raw", "RGB" 或 "BGR", stride)` 直接建图，BILINEAR 缩放，去掉 `update_idletasks()`，chase 和顶视限 10 Hz。实测 chase 一帧降到 3.2 ms。
   - 不修：开着仿真页，整个 Studio 发卡。

10. **仿真页布局把顶视和地图压扁**（`ui/studio.py:1127-1131`）
    - 是什么：仿真页四个面板的网格布局。
    - 问题：行只设了权重，每个画面按自己当前尺寸缩放，小的一直小。实测 1500×960 窗口里顶视 86×65 px，地图 578×78 px。
    - 修：行和列加 `uniform`。实测改后顶视 216×162 px，地图 710×172 px。
    - 不修：顶视和轨迹地图基本看不了。

11. **地图每 80 ms 全量重画，历史扫描卡住界面**（`ui/studio.py:2136-2201`、`:475`）
    - 是什么：轨迹地图的绘制，以及启动、训练结束时扫描所有 eval.json。
    - 问题：地图每次 `delete("all")` 后重画网格、障碍物和 3000 点平滑折线（15 ms）。
      `rglob("eval.json")` 扫整个 `$DATA_ROOT/uav_rgb`（连 3dgs-venv 和 pip 缓存一起），实测 1.57 s，跑在主线程。
    - 修：静态层只画一次，轨迹和机体用 `coords()` 更新；扫描改成 `os.walk` 剪掉 venv 和缓存目录，放后台线程。
    - 不修：启动和每次训练结束都会卡一下，仿真页 CPU 占用高。

12. **状态栏被每帧覆盖，Gazebo 停不干净**（`ui/studio.py:2003, 2049, 3006`）
    - 是什么：仿真页状态栏，以及 Studio 自己启动的 headless Gazebo。
    - 问题：「Gazebo 已退出 rc=…」这类消息下一个 80 ms 就被流状态覆盖。停止只发一次 SIGINT，不升级到 SIGTERM/SIGKILL；
      Studio 没注册信号处理，Ctrl+C 关掉后 Gazebo 成了孤儿进程。
    - 修：流状态单独用一个变量；停止时超时升级；注册信号处理，统一走 `_on_close`。
    - 不修：错误信息看不到；孤儿 `gz sim` 占着 GPU，下次启动被「已运行」拒绝。

13. **录像叠字乱码、帧重复、残留混帧、浏览器放不了**（`sim/tools/record_views.py:55-60, 67-68, 80, 218`）
    - 是什么：闭环评测的三视角录像。
    - 问题：叠字里的「·」和中文被 OpenCV 的 Hershey 字体画成「?」；15 Hz 的 chase 按 100 ms 间隔抽帧，约每 4 帧有 1 帧重复；
      帧文件用追加模式打开，残留目录会混进上一次的帧；mp4v 编码在浏览器和编辑器预览里放不了。
    - 修：叠字只用 ASCII；按 `ts // period` 分桶取帧；用 `"wb"` 打开；编码试 `avc1`，OpenCV 不支持就用 VP80 写 .webm（本机没装 ffmpeg，未验证）。
    - 不修：录像看不清时间戳，回放节奏不对，报告里的视频点不开。

14. **3DGS 录像快 2.5 倍，帧数和转角日志不对**（`sim/3dgs/eval_3dgs.py:84, 145`、`sim/3dgs/video.py:31`、`sim/3dgs/collect_3dgs.py:176`；转角是 AUDIT #13）
    - 是什么：3DGS 评测生成的视频和每步日志。
    - 问题：每帧代表 hold = 0.5 s，视频按 fps=5 写，播放速度是仿真时间的 2.5 倍；`compose_rgb_video` 返回文件数而不是实际写入帧数；
      `dyaw_deg` 用度减弧度，实测左转 9.65° 记成 553°。
    - 修：`fps = 1 / hold`；返回实际写入数；两边先统一成度再求环绕差。
    - 不修：看视频会以为飞得很快；转向审计和标定用的是错数。

15. **三套互相矛盾的占位动力学**（`sim/tools/collect.py:141-231`、`sim/tools/cf_sil.py`、`sim/tools/cf_blackbox.py`、`sim/dynamics/*.json`、`sim/tools/teacher_predictive.py`、`rl_teacher/core.py:107`）
    - 是什么：cf_stab、cf_sil、cf_blackbox 三种「模仿 CF-Drone」的执行模型。
    - 问题：延迟 0.15 / 0.02 / 0.15 s，前进终速 0.34 / 0.3 / 1.38 m/s，偏航 0.6 / 0.6 / 0.785 rad/s，全部 `calibrated=false`。
      cf_sil 的 250 Hz 线程只能拿到约 50 Hz 的位姿，五次里有四次 dt=0。同样的常数还抄在 rl_teacher 和 teacher_predictive 里。
    - 修：SITL 过了 §2.4 门禁后，三套连同测试一起删，21 个引用它们的文件改成只认 SITL。
    - 不修：每多一套，就多一套要维护、要解释、不能混报的数字。

16. **仿真相机是理想针孔**（`sim/worlds/uav_rgb.sdf:191-211`、`sim/3dgs/scene.py:262-268`）
    - 是什么：学生看到的 RGB 相机。
    - 问题：没有畸变、噪声、运动模糊、曝光变化和延迟，安装位置是 X3 尺度的机身前 0.2 m；真相机的参数一项都没有。
    - 修：先标定真相机；在学生预处理入口（`sim/tools/student.py`）加一个统一的相机后处理，Gazebo 和 3DGS 共用。
    - 不修：图像分布和真机差一截，场景再逼真也补不回来。

### 可以顺手修

17. **位姿消息省略 0 值字段时，UAV 从地图上消失**（`ui/studio.py:151`）
    - 是什么：Studio 解析 `/model/x3/pose`。
    - 问题：`float(pos[k])` 遇到缺字段就整条丢弃；protobuf 转 JSON 默认省略值为 0 的字段，出生点 y=0 时会缺 y。本轮没有在实机消息上确认。
    - 修：`float(pos.get(k, 0.0))`，和下一行四元数的写法一致。
    - 不修：飞机停在 y=0 时地图上没有它，相机都显示 WAIT。

18. **轨迹、底图和 chase 视角会误导**（`ui/studio.py:742, 1792, 1936, 2215`、`sim/worlds/uav_rgb.sdf:218-219`）
    - 是什么：轨迹地图、障碍物底图和第三人称视角。
    - 问题：轨迹只在连接、断开时清空，重开 live demo 会画出一条跨图直线；底图来自界面里选的 SDF，不一定是正在跑的世界；
      chase 相机固定在机体上，跟着俯仰和滚转（X3 最多约 11.5°，真机 STAB 最多 30°）。
    - 修：开新一集时清轨迹；地图上写出 SDF 文件名，和运行中的世界不一致时标「未核对」；chase 改成只跟位置和偏航的跟随视角。
    - 不修：画面会误导你判断轨迹和姿态。

19. **3DGS 颜色只用了 0 阶球谐，320 px 下会闪**（`sim/3dgs/scene.py:74`、`sim/3dgs/renderer.py:97`）
    - 是什么：3DGS 渲染的颜色和抗锯齿。
    - 问题：Callinstrasse 带 3 阶球谐（SH），读入时只留了 DC 项，随视角变化的高光和反光没了；原图 5–6K 宽，渲染 320 px，多数高斯小于 1 像素，classic 模式下细结构会闪。
    - 修：读 `f_rest`、传 `sh_degree=3`；`rasterize_mode="antialiased"`，或者 2 倍分辨率渲染再缩小。
    - 不修：渲染图比真实相机更干净，迁移时多一层差距。

## 6. 需要你拍板

- **D1 机型**：E1 MINI（ESP32，约 118 mm，约 80 g）还是 E1 Nano（ESP32-S3，50 mm，约 25 g）？固件注释和 `cf_sil_v1.json` 都指向 MINI。
- **D2 高度由谁来稳**（四选一）：
  - (a) 官方「定点模块」（BMP388 + QMC5883 + VL53L1X + PMW3901）加官方发布的固件。官方文档说官方固件会自动开定高、定点，
    开源代码里需要自己开发（[扩展模块](https://docs.cherglowtech.com/e-series/e1-mini/extended-module)）。上手最快，但这部分飞控代码拿不到，SITL 只能黑盒辨识。
  - (b) 把 ToF（VL53L1X，可加 PMW3901 光流）接到 LicheePi，在伴飞侧做定高、定速，再折算成油门杆和俯仰杆。固件不改，SITL 能逐行复现。
  - (c) 在开源固件里实现 ALTHOLD。最干净，但要改固件、上台架验证。
  - (d) 第一阶段人手控油门，模型只管俯仰和偏航。最快上机，只适合先采真机数据。
  - 建议：坚持固件不改选 (b)，能改固件选 (c)。
- **D3 速度怎么办**：没有光流时，FORWARD_SLOW 只能是「按某个倾角保持 hold 秒」，SAFE_NEUTRAL 只能是「回中滑行」，
  现在的单帧无记忆学生看不出自己在动，需要多帧输入。有光流做定速，现在的「定速前进、悬停」语义在真机上才成立。
- **D4 指令通道**：CRSF 摇杆模拟（固件不改；LicheePi 串口要能出 420000 波特率，Linux 下要用 termios2，现有 `uart_action.py` 的波特率检查会拒绝；
  限幅、看门狗、人工接管都要在 LicheePi 侧做），还是自定义 UART 协议（固件要加解析器，即 `ALVLN/docs/08` 的 PR-F1）。
- **D5** 能否给固件日志加电机占空比、原始 IMU、电池电压三列（只为辨识，不动控制）。
- **D6** SITL 验收后，是否删除 cf_stab / cf_sil / cf_blackbox。

建议的下一步：你定了 D1，我先做不依赖实测的一步，把 CF-Drone 控制代码原样编进 SITL 库，
用 Flix 公开的 65 g 参考机参数跑悬停和打杆自检，证明链路通；你测完 §2.3 的参数再换成实测值，接到 3DGS 路线。
