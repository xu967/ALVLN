### 6. 瓶颈与建议
- 瓶颈是 **1 kHz 物理循环**（DART + 接触 + 插件每步一次固件 tick），不是渲染也不是话题：aux/noaux 的 RTF 相同（2.31 vs 2.27–2.40），gz 解锁时恰好吃满 ~2 核（物理线程 + 传感器线程），桩库/真库 RTF 差 <3%，state 200 Hz 零抖动、late_actions 0。
- 相机 **10 Hz** 够用：hold 1 s 每窗只消费 1 帧，RGB/深度同戳配对 0 ms（偶发 1/30 步深度晚到一帧 = 100 ms，仍在 `DEPTH_STALE_NS` 门内）。提高帧率只会增加渲染负担，不改善数据。
- `--no-aux-cameras`：锁 1.0 时每步快 17%（1.09→0.90 s）；解锁时无差别。录 demo 视频时才开辅助相机。
- 实例数：12 核 cgroup 下 4 实例 6.8 核、每步 0.55 s；6 实例 8.6 核、每步 0.86 s、吞吐只多 10%。**建议 4 实例**。
- 解锁 RTF：每步 0.9 → 0.53 s（1.7×）；代价是观测→派发的 I/O 延迟（~50 ms 墙钟）在仿真里放大到 ~85 ms（hold 1 s 的 8.5%，锁 1.0 时 5%），`action_window` sim_dt 的 cv 从 0.3% 升到 2.5%。模板仍锁 1.0（与 X3 同口径）；本次解锁测量用的是模板副本（只改 `<real_time_factor>` 为 0，`agent-gz/uav_rgb_e1_unthrottled.sdf`，经 `--template` 传入），仓库里**没有**解锁开关。
- ≥300 集（40 步）估算：锁 1.0、noaux、4 实例：每集 ≈ 6 s 启动 + 7.5 s 起飞 + 40×0.9 s ≈ 50 s → 300 集 ≈ 63 min；解锁 4 实例 ≈ 33 s/集 → ≈ 41 min。两者都可接受，**默认建议锁 1.0 + `--no-aux-cameras` + `--instances 4`**，赶时间再考虑加解锁开关。

## 风险与遗留
- 真库采集在 `calibrated=false` 参数上，数字不能与 X3 档混报（manifest 已分档）。
- 首条 gz-transport 消息偶发丢失现在只对 `reset` 做了重发；`arm_takeoff` 之后的动作消息丢失会表现为该步无动作（late_actions/位移异常），collect 的每步位移检查能看见但不会重发。
- RTF 解锁时 I/O 延迟在仿真里放大（见 §6），若将来加解锁开关，建议同时把 `pose_gap`/`io` 写进 manifest `performance` 便于审计。
- `collect_parallel` 对 cf_sitl 的 `camera_rate_hz` 只记 CLI 参数（没传则 None），模板实际值在各集 scene meta 里。
