# E3 修复：专家滞回 + 高度保持（数据质量）

- 时间：2026-10-28 23:34
- 范围：`sim/tools/teacher.py`、`sim/tools/collect.py`
- 结论：完成（实跑验证：摆振消失、高度稳定、碰撞检测未回退）

## 做了什么

E3 采集闭环交付后，其自述暴露两个会**污染训练标签**的问题，本次修复：

1. **专家无滞回 → 左右摆振**（`teacher.py`）
   - `expert_action` 新增 `prev_action` / `switch_margin=0.75`：两侧都能转时保持上次方向，
     只有另一侧空出 0.75m 以上才反向；但**滞回不能压过安全**（原方向侧被堵时仍必须换向）。
   - 自测从 6 项增到 9 项，新增 3 条滞回用例（小幅差异保持 / 明显更空换向 / 不覆盖安全）。

2. **高度持续下沉 → 加到保持**（`collect.py`）
   - 原实现所有 twist 的 `z:0` 是「零垂直速度」不是「保持高度」，速度控制器不会自动悬停，
     实测一次 8 步 run 从 z=1.78 掉到 1.23。
   - 新增 `make_twist(action, vz)` + `altitude_vz(pose)`（带回死区的 P 控制），
     `collect_one` 每步按当前高度算 vz。**vz 是仿真执行器细节，不是模型输出**——模型仍只吐 0..3 四动作。
   - `main()` 维护 `prev_action` 传给下一步。

## 过程中自己踩的坑（重要，写下来）

- **第一版高度 P 增益设 0.8，把无人机摆成 1.19→2.52→0.55 的 2m 震荡**。
  根因：一步实际约 **2.3s sim-time**（不是 `--hold` 的 0.5s，深度/位姿/接触的 `gz topic -e` 开销远大于 hold），
  控制周期这么长时 0.8 的增益必然过冲。改为 `Z_KP=0.25` + `Z_DEADBAND=0.2` 后稳定在 1.86。
- **`pkill -f 'gz sim'` 会杀掉自己**：本会话的 shell 命令行里就含这个字符串，`pkill -f` 自匹配，
  连续两次把自己的命令打断（exit 144）。改法：用 `setsid` 起进程组 + `kill -- -PGID` 收尾；
  残留的 `ruby` server 用 `ps` 按 comm 精确找 PID 再 kill。
- `gz sim -s` 会留下 `ruby` 子进程，杀父进程不一定能带走，必须显式清理，否则多 server 互相污染话题。

## 没做什么

- **没有重跑 E3 的完整 episode 格式验证**（manifest/actions/oracle/contact 证据）。
  - 原因：本次只改了动作选择与 twist 构造，episode 落盘代码未动；且碰撞路径已单独实跑验证。
- **没有解决「专家过早转向、绕开障碍后一路飞走」的策略质量问题**。
  - 原因：`min_clear=2.0m` 让专家在 2.2m 外就转向，本机场景下它转向后沿 -y 一飞到底（y 到 -4.74），
    从未真正穿行障碍之间。这是**场景/策略设计问题**，不是 bug；要做出有穿行、绕行、逼近的多样轨迹，
    需要重新设计场景布局与 min_clear，属正式采集前的任务。
- 没做 episode 间 reset（同 server 连跑两 episode 会被残存 twist 污染，E3 已记录）。
- 没做场景随机化、sim-time 精确对齐、128×128 降采样（沿用 E3 的遗留清单）。

## 待确认

- `switch_margin=0.75m`、`Z_KP=0.25`、`Z_DEADBAND=0.2` 三个超参是否合适；正式采集前应用更长 run 调。
- 巡航高度 1.8m 是否合理（立柱高 3m，1.8m 仍被挡；若想从柱顶飞越需 >3m）。

## 风险与遗留

- 控制周期 ~2.3s 对真实飞控来说太慢；采集吞吐与物理保真度都受限，长期要换 C++ gz-transport 直连。
- 专家转向后不回头，采集到的轨迹以「绕开就跑」为主，缺乏「贴近障碍再穿行」的困难样本。
  训练出来的策略可能只会早转向，遇到窄缝会卡死——**这一点必须在正式采集前解决**。
- `SAFE_NEUTRAL` 在实测中出现过一次（step 1），说明深度带内确实出现三向皆堵的瞬间，
  若频繁出现应检查 min_clear 是否过大。
