# CUDA 内核审核（linear / conv2d / softmax-CE）

- 时间：2026-10-28 23:34
- 范围：`src/linear_cuda.cu`、`src/conv_cuda.cu`、`src/softmax_cuda.cu` 及其头文件、三个对拍测试、doc 04 §6 N1-N6 矩阵。
- 方式：只读审核，未修改任何源码。独立构建目录 `/tmp/audit-cuda`（未使用 `src/build`）；边界探针在仓库外 `/tmp/audit-probe/probe.cu`。
- 发现总数：10 条（必须修 2 / 应该修 4 / 可以改 4）。

本批代码是三组手写 CUDA 内核：Linear 前向/反向（dW/db/dx）、Conv2d 前向/反向（NCHW、stride=1、pad 可配）、softmax 交叉熵 loss/grad。每个包装函数都在内部临时 `cudaMalloc`/`cudaMemcpy`、逐 kernel 用 `cudaGetLastError` + `cudaDeviceSynchronize` 检查，再把结果拷回 host `Tensor`；配套三个 CPU/CUDA FP32 对拍自检（doc 04 §6 N3）。

最严重三条：**#1 int32 规模算术溢出**（已实跑：8.59 GB 输出直接退出；16 GiB 输出静默返回 99.998% 错误的张量）、**#2 空张量 N=0 直接杀死进程**（已实跑，6 个入口全中，且退出路径泄漏设备缓冲）、**#3 所有 CUDA 错误（含 OOM）用 `std::exit`**（库无法捕获、析构与 checkpoint 落盘全部跳过）。

## 必须修

### 1. 规模/索引算术全用 `int`，超过 2^31 元素时溢出：轻则进程退出，重则静默错误结果

- **位置**：
  - `src/conv_cuda.cu:56`、`:85`、`:130`（kernel 内 `const int total = ...`）、`src/conv_cuda.cu:190`、`:191`、`:224`、`:229`、`:233`（host 侧 total/blocks）
  - `src/linear_cuda.cu:54`、`:68`、`:93`（kernel 早退边界）、`:118-120`、`:127`、`:149-151`、`:169-171`（`cudaMemcpy` 的字节数写成 `n * out * sizeof(float)` 这类 int 乘法）、`:122`、`:153`、`:157`、`:161`（blocks）
  - `src/softmax_cuda.cu:72`、`:134`、`:135`（`n * c`）
- **这是什么**：所有元素总数、block 数、kernel 内偏移都用 32 位 `int`。卷积的分配用 `long long`（`conv_cuda.cu:180-183`），但 launch 用的 `total`/`blocks` 仍是 `int`；linear 连 kernel 索引都是纯 int。
- **问题**（均已实跑复现，探针见 `/tmp/audit-probe/probe.cu` case 18/20）：
  - 硬退出：`Conv2d m(1, 32768, 1, 1, 0)` + `x=[1,1,256,256]`，真实输出 32768×65536 = 2^31 个元素。`int total` 回绕成负数，`blocks` 为负，launch 报 `cudaErrorInvalidConfiguration`，`check_after_kernel` 调 `std::exit(1)`（实测 0.4 s，分配 8.59 GB 后退出）。
  - **静默错值（更严重）**：`Conv2d m(1, 65537, 1, 1, 0)` + `x=[1,1,256,256]`，W=0、b=1，正确输出应处处为 1.0。真实元素数 4,295,032,832 = 2^32 + 65,536，`int total` 回绕成 65,536，只有前 65,536 个输出被计算。实测返回 `numel=4295032832` 的张量，`y[0..65535]=1`、`y[65536]=0`、`y[100000]=0`、`y[last]=0`，rc=0、无任何报错（18.5 s，16 GiB 输出）。也就是说 >99.998% 的输出是未写入的设备内存，训练时会被当成正常数据继续用。
  - 线性层同类问题：`linear_cuda.cu:118` 的 `cudaMemcpy(..., n * in * sizeof(float), ...)` 在 `n*in` 超 2^31 时先按 int 溢出再转 `size_t`，分配却按 `size_t` 算，两者不一致；2^31~2^32 之间通常是 memcpy 失败退出，2^32 以上可只拷一小段、其余设备缓冲未初始化（未实跑，需 ~17 GB host 张量）。
  - 触发门槛：≥2^31 个输出元素（≈8.59 GB 设备内存）即可硬退出，≥2^32（≈17.2 GB）可静默错值。当前 doc §4 的目标形状（[1,3,224,384]、batch 64）离阈值还有约 4 个数量级，但这张卡有 22.5 GB 显存，大 batch/大特征图或未来换更大的 head 是可能踩到的；这也是 doc §6 要求测“极大”输入时最该覆盖的一类。
- **建议的最小平修法**：所有 `total`/`blocks`/偏移改用 `long long`（kernel 索引也统一 `long long`，conv 已有部分这样写，linear 完全没有）；launch 前显式检查 `total > INT_MAX`（以及 `total > gridDim.x 上限 * blockDim.x`）并抛 `std::invalid_argument`，宁可在入口失败也不要回绕。`cudaMemcpy` 的字节数同样先用 `std::size_t` 算好。

### 2. N=0 / 0 元素输入：0 个 block 的 kernel launch 失败，`std::exit(1)` 杀死进程，退出路径泄漏设备内存

- **位置**：`src/linear_cuda.cu:122-124`、`:153-163`；`src/conv_cuda.cu:190-194`、`:224-236`；`src/softmax_cuda.cu:114-116`、`:134-137`。相关：`cudaMalloc(0)` 在 CUDA 12.8 上返回成功 + nullptr（已实测），所以失败点不是分配，而是 `blocks = (0 + 255) / 256 = 0` 的 launch。
- **这是什么**：形状校验只检查了维度匹配，没有处理 n=0（以及 conv 的 H=0/W=0）这种合法但为空的张量。
- **问题**（探针实跑，每个入口单独进程）：
  - `linear_forward_cuda` + `x=[0,8]`、`linear_backward_cuda` + N=0、`conv2d_forward_cuda` + N=0、`conv2d_backward_cuda` + N=0、`softmax_ce_loss_cuda`/`softmax_ce_grad_cuda` + `logits=[0,5]`：6 个入口全部打印 `CUDA kernel ...: invalid configuration argument` 后 rc=1，进程被 `std::exit` 终止。
  - 同一输入 CPU 参考是正常的：`linear_forward` 返回空张量、`conv2d_forward` 返回空张量、softmax loss 返回 NaN（0/0）、grad 返回空张量（已实测）。也就是说 CUDA 与 CPU 在空 batch 上行为不一致，且 CUDA 侧是硬退出。
  - 卷积反向是“半途死”：dW/db kernel 的 block 数非零会先跑完，最后 dx kernel（`conv_cuda.cu:130` 的 `total=0`）才失败退出。
  - 退出路径不走 `DeviceBuf` 析构，memcheck 实测泄漏：linear 144 B / 2 次分配、conv 228 B / 2 次、softmax 8 B / 1 次（缓冲越大泄漏越多）。
  - 失败场景：训练/评测数据管线过滤后出现空 batch（最后一个不完整 batch、按标签过滤、空验证集），一个合法空张量就让整个训练进程退出。
- **建议的最小平修法**：在形状检查之后、任何 `cudaMalloc`/launch 之前早退：`if (n == 0)`（conv 再加 `h == 0 || wd == 0`）直接返回形状正确的空/零张量；loss 返回 0.0f 并与 CPU 参考对齐（CPU 现在是 NaN，需同时决定语义并加测试）；softmax 的 `c == 0` 直接抛 `std::invalid_argument`。

## 应该修

### 3. 所有 CUDA 运行时错误都用 `std::exit(EXIT_FAILURE)`，调用方无法捕获，析构与落盘被跳过

- **位置**：`src/linear_cuda.cu:15-23`（`CUDA_CHECK`）、`:26-33`（`check_after_kernel`）；`src/conv_cuda.cu:15-23`、`:26-33`；`src/softmax_cuda.cu:16-24`、`:27-34`。
- **这是什么**：分配失败、H2D/D2H 拷贝失败、launch 配置错误、kernel 执行错误，全部打印后 `std::exit`。这与“形状错误抛 `std::invalid_argument`”的接口契约不一致。
- **问题**：具体场景是在共享的 22.5 GB GPU 上（本机就同时有另一个 agent 在构建/可能跑测试），或 batch 调大后，`cudaMalloc` 返回 `cudaErrorMemoryAllocation` → 训练进程立即退出：调用方没法 catch 后减小 batch/重试；`std::exit` 跳过所有栈上析构（打开的文件、日志、checkpoint 写入都会断在半路），`DeviceBuf` 也不释放（#2 已用 memcheck 证实这条路径确实泄漏）。对 parity 测试“失败即退出”可以接受，但这是给训练器用的库接口。
- **建议的最小平修法**：`CUDA_CHECK` 改为抛 `std::runtime_error`（RAII 会自然释放已分配缓冲），或返回 `cudaError_t` 由上层决定；只有测试 `main` 里再选择打印退出。

### 4. `test_softmax_cuda` 的“label 越界”自检实际走的是 labels 数量不匹配分支，范围检查从未被测试（false green）

- **位置**：`src/tests/test_softmax_cuda.cpp:61-69`（`const std::vector<int> bad = {2, 9};` + n=6 行 logits）。
- **这是什么**：注释写的是“label 越界应抛异常（防越界读）”，但传入的 labels 只有 2 个，而 logits 有 6 行；`check_dims`（`softmax_cuda.cu:91-93`）先命中数量检查。
- **问题**：实测该调用抛出的消息是 `"labels 数量与 logits 行数不一致"`，不是 `"label 越界"`。也就是说 `softmax_cuda.cu:94-96` 的 `label >= c` 越界保护一次都没被测试到：把这层保护删掉，现有测试仍然 PASS，而 kernel 里的 `labels[i]`/`row[label]` 会真的越界读设备内存。
- **建议的最小平修法**：改成 6 个 label、其中一个是越界值（如 `{2,0,3,1,4,9}`），实测会抛 `"label 越界"`；数量不匹配可以另留一条用例。

### 5. `test_conv_cuda` 的形状异常自检打的是 CPU 参考函数，CUDA 包装的校验完全没测到；linear 没有任何负例

- **位置**：`src/tests/test_conv_cuda.cpp:122-133`（第 128 行 `(void)conv2d_forward(m, bad_x);`）；`src/tests/test_linear_cuda.cpp:34-93`（无负例）。
- **这是什么**：这个测试在 `test_conv_cuda` 里，注释是“形状不匹配应抛异常（防越界）”，但调用的是 CPU 的 `conv2d_forward`，不是 `conv2d_forward_cuda`。
- **问题**：把 `conv_cuda.cu` 的 `check_dims` 整个删掉，现有测试仍然全绿；`conv2d_backward_cuda` 的 dy 形状检查、`linear_forward_cuda`/`linear_backward_cuda` 的形状检查同样没有任何测试覆盖。CUDA 侧这些检查本身是对的（探针实测分别抛出 `"conv2d_cuda: x 形状必须为 ..."`、`"conv2d_backward_cuda: dy 形状必须为 ..."`、`"linear_forward_cuda: x 形状必须为 ..."`），所以这是纯覆盖盲区，不是已存在的错误行为。
- **建议的最小平修法**：负例改调 CUDA 版本（`conv2d_forward_cuda` + 通道不匹配、`conv2d_backward_cuda` + dy 尺寸不匹配），linear 加一条 `x` 列数不匹配的 `invalid_argument` 用例；CPU 参考的负例可以保留但要分开标注。

### 6. doc 04 §6 要求的边界测试缺失：空输入、NaN/Inf、随机输入、非方核、注入 bug 自检

- **位置**：`src/tests/test_conv_cuda.cpp:65-102`（两组配置都是 3×3 核）、`src/tests/test_softmax_cuda.cpp:30-38`（只有确定性公式）、`src/tests/test_linear_cuda.cpp:37-62`；对照 `../TinyAerialVLN_Final_V8/docs/04_CPP_CUDA_IMPLEMENTATION.md:102`（要求测 padding、长度 0、极大 logits、NaN/Inf，并要求“故意注入一个转置/标签映射 bug”验证测试能抓到）。
- **这是什么**：现有测试是确定性数值、N≥1、C=5、核 3×3、logits ±8。
- **问题**：
  - N=0：CUDA 直接退出（#2），现有测试也从不覆盖。
  - NaN/Inf：实测 `logits={0,+inf,1,-inf}` 返回 `loss=nan`、grad 全 nan；`{0,nan,1}` 同样，没有任何报错或断言（CPU 参考行为相同，所以 N3 parity 仍是“一致”的）。doc §8 要求训练器检测 `TRAIN_NONFINITE_METRIC`，当前内核层静默放行。
  - 随机输入：N3 要求“随机种子”一致性，现有测试全是手写公式、没有随机化对拍（本次审核探针用 `sin/cos` 覆盖了 n=257 的 linear、k=3×5+pad=2 的 conv、±100 logits，均通过）。
  - 非方核：两组配置 kh=kw=3，任何把 kh/kw 角色混用的回归（例如输出尺寸公式误用 kw、ki 上界误用 kw）在 kh==kw 时数值完全相同，测试抓不到。本次 3×5 探针通过，说明当前实现没问题，但测试无法防回归。
- **建议的最小平修法**：加一组 `kh=3, kw=5, pad=2` 的 conv parity；加 N=0 用例（与 #2 的修复一起）；加 ±Inf/NaN 用例，明确期望（抛异常，或与 CPU 一致的 NaN parity）；加一组固定种子的随机输入对拍；如条件允许，在 CI 里做一次“注入转置/标签映射 bug 必须让测试变红”的自检。

## 可以改

### 7. 每个 kernel 后全量 `cudaDeviceSynchronize` + 每次调用临时 malloc/free：固定开销实测 285-354 µs/call

- **位置**：`src/linear_cuda.cu:26-33`、`:113-120`；`src/conv_cuda.cu:26-33`、`:180-188`；`src/softmax_cuda.cu:27-34`、`:105-112`。
- **这是什么**：每个 kernel launch 后先 `cudaGetLastError` 再 `cudaDeviceSynchronize`；每次调用重新 `cudaMalloc`/`cudaFree` 全部缓冲，最后同步 D2H。
- **问题**：实测（Release、RTX 2080 Ti、GPU 空闲）一个 `N=16, in=8, out=4` 的 linear：前向 285.4 µs/call、反向 354.4 µs/call，计算本身只有微秒级，几乎全是分配/同步开销。按 20 层网络估算，仅这层固定成本每 step 就是 ~10 ms 量级；而且 `cudaDeviceSynchronize` 等的是当前 context 里所有 stream 的活，若上层同时跑推理/数据拷贝，会被这些调用无故拖住。另外 `cudaMalloc`/`cudaFree` 本身会隐式串行化。worklog 已把它标成 parity 专用 shortcut，这里补上实测数字：训练器不能直接复用这些函数。
- **建议的最小平修法**：parity 测试保持现状；训练路径另做持久 `DeviceBuf` 复用 + 只在 step 边界同步（或返回设备张量、由调用方统一同步）。至少把每个函数的多次同步合并成一次。

### 8. softmax grad 每个元素都重算整行 max/sum，复杂度 O(N·C²)

- **位置**：`src/softmax_cuda.cu:68-82`。
- **这是什么**：grad kernel 每个线程（每个元素）都扫两遍整行，重新算 `mx` 和 `sum`。
- **问题**：C=1024、N=64 时是约 6700 万次 `expf`，而按行算只需约 6.5 万次（~1000 倍）。当前动作头 C=4 完全无感（实测 parity 5.68e-14），但 doc 里未来有文本/词表类 head，一旦 C 上千这条会明显拖慢训练。
- **建议的最小平修法**：每行一个 block/warp 算一次 max+sum（shared memory 归约）后写整行梯度，或拆成“先算每行 max/sum 存行缓冲，再算梯度”的两 kernel 方案。

### 9. 没有校验 `m.W`/`m.b` 的元素数，权重张量被赋错大小时会 host 越界读

- **位置**：`src/linear_cuda.cu:114`、`:119-120`、`:143`、`:150`；`src/conv_cuda.cu:181`、`:187-188`、`:216`、`:221`。
- **这是什么**：包装只校验 `x` 的形状，直接按 `out*in`（conv 再加 `kh*kw`）从 `m.W.data()` 拷 `out*in*sizeof(float)` 字节。
- **问题**：具体场景：`Linear m(8,4); m.W = Tensor::zeros({4}); linear_forward_cuda(m, x);` 会从只有 16 字节的 host vector 读 128 字节（heap 越界读，UB），kernel 拿到垃圾权重且无任何报错；CPU 参考有同样假设。当前调用方都经构造函数，暂时安全；但计划中的 checkpoint 加载器会给 `W/b` 重新赋值，这是现实的可达路径。
- **建议的最小平修法**：入口校验 `m.W.numel() == (size_t)out*in && m.b.numel() == (size_t)out`（conv 为 `out*in*kh*kw` / `out`），不符抛 `std::invalid_argument`。

### 10. 测试的 `max_abs_err` 不先比形状，形状回归时会变成 host 越界而不是干净 FAIL

- **位置**：`src/tests/test_linear_cuda.cpp:24-30`；`src/tests/test_conv_cuda.cpp:24-30`。
- **这是什么**：`for (i < a.numel()) ... b[i]`，默认 `a`/`b` 元素数相同。
- **问题**：若 CUDA 包装回归成不同形状（例如把 `[N,out]` 返回成 `[N,in]`），`b[i]` 会越界读 host 内存（UB、可能段错误），测试可能崩而不是给出可读的 FAIL。这类回归正是这些测试要抓的。
- **建议的最小平修法**：先比较 `dims()`/`numel()`，不一致直接返回一个大误差并打印，或 `check(false, "shape mismatch")`。

## 重点核对过、未发现问题的点

- **越界**：8 个 kernel 的 `idx >= total` 早退都覆盖了各自全部输出维（linear 的 `n*out`/`out*in`/`n*in`；conv 的 `n*out*oh*ow`、`out*c_in*kh*kw`、`n*c_in*h*wd`；softmax 的行、`n*c`）。conv padding 的 `ih/iw` 上下界判断与 CPU 参考一致。memcheck 在既有测试和额外边界输入（C=1、±100 logits、3×5 核 pad=2、257 行 linear、NaN/Inf）上都是 0 error。
- **db kernel 只按 `out` 起线程是正确的**：conv 每个线程独立累加 `n*oh*ow` 个 dy，linear 累加 n 个，没有漏算/重复；racecheck 0 hazard。
- **竞争**：softmax 的 `atomicAdd(double*)` 是原子操作，不是数据竞争；归约顺序不确定只影响 bitwise 可复现性（double 级，再 cast 回 float 后本机实测 loss 差为 0）。racecheck 只检测 shared memory 竞争，本批 kernel 完全不用 shared memory，所以 0 hazard 是预期结果、不能当作全局访存无竞争的证明；但除 atomicAdd 外每个线程只写自己的输出，逻辑上无竞争。
- **数值稳定性**：softmax 先减去行最大值，`sum >= 1`，有限 logits 下 exp 不会上溢；grad 的 1/N 与 CPU 一致。C=1、±100 logits 的 parity 均通过（loss 差 0、grad 5.68e-14）。
- **泄漏**：正常路径没有 `DeviceBuf` 之外的裸 `cudaMalloc`；`--leak-check full` 三个测试均 0 bytes。形状不符时在第一次 CUDA 调用之前就抛异常（sanitizer 显示 "Target application terminated before first instrumented API call"），不会泄漏。唯一的泄漏窗口是 `std::exit` 路径（#2/#3）。
- **同步语义**：所有操作都在 default stream，kernel 后同步再 D2H，返回 host Tensor 的顺序是正确的；没有发现“本应异步却依赖顺序”的正确性问题（性能代价见 #7）。
- 构建产物只含 `sm_75`（`cuobjdump -lelf` + CMakeCache 确认），符合机器约束。

- `compute-sanitizer --tool memcheck --leak-check full ./test_{linear,conv,softmax}_cuda`：
  - 三个均 `ERROR SUMMARY: 0 errors`、`LEAK SUMMARY: 0 bytes leaked in 0 allocations`。
- `compute-sanitizer --tool racecheck ./test_{linear,conv,softmax}_cuda`：
  - 三个均 `RACECHECK SUMMARY: 0 hazards displayed (0 errors, 0 warnings)`（注意上面的局限：只查 shared memory）。
- 额外探针（仓库外）：5 组边界输入 memcheck 均 0 error / 0 leak；N=0 探针在 memcheck 下报 `cudaErrorInvalidConfiguration` 并泄漏 144/228/8 bytes（缺陷 #2 的证据）；16 GiB 溢出探针 18.5 s 正常返回错误张量，sanitizer 无告警（它不是越界，只是少算了，见 #1）。

## 结论

这批 kernel 在“N≥1、C≥1、有限 logits、元素数 < 2^31、调用方传对 W/b”的正常路径下逻辑正确：CPU/CUDA parity、补跑的扩展形状对拍、memcheck/racecheck 都干净。真实缺陷集中在 32 位规模算术（#1，已复现静默错值）、空张量入口（#2，进程退出 + 泄漏）、库级错误处理（#3，OOM 即杀进程）以及验证测试的盲区（#4-#6，自检打错目标或漏测）。在 224×384、batch≤64 的目标形状下 #1/#2 暂不会被触发，但 #3 在共享 GPU 上有现实风险；#4/#5 意味着目前的“全绿”对 CUDA 侧校验的证明力比看上去弱。
