## 这批代码做什么

`Tensor` 是 CPU 连续 row-major FP32 张量；`ops_cpu.cpp` 实现 Linear 前/反向、stable softmax 交叉熵 loss/grad 和 FP64 有限差分 gradcheck；`conv_cpu.cpp` 实现 NCHW、stride=1、pad 可配的 Conv2d 前/反向与 FP64 gradcheck；`action.cpp` 把连续速度量化成四动作。测试用手写 `main()` 返回码做断言，CUDA 侧用 CPU/CUDA parity 当 oracle。目的是给后续 CUDA 训练内核提供数值参考与对拍基线。

## 必须修

### 1. `gradcheck_conv2d` 不校验输入，rank 不足时越界读，形状错误时假通过
- 位置：`src/conv_cpu.cpp:192-208`（`x.dims()[0/2/3]` 在 193/195/196，`oh/ow` 在 201-202）。
- 问题（两种具体失败）：
  1) `gradcheck_conv2d(m, Tensor::zeros({1,1,4}))`：`x.dims()[3]` 越界读。实测 ASan `heap-buffer-overflow READ of size 8 ... conv_cpu.cpp:196`（dims 由 initializer_list 构造，容量恰为 3，读出分配边界）。
  2) `Conv2d m(1,2,3,3,1); gradcheck_conv2d(m, Tensor::zeros({1,3,4,4}))`：`c_in` 用 `m.in=1` 而不是 `x.dims()[1]=3`，只把 x 的前 1 个通道当成输入，**静默返回 0**；而 `conv2d_forward` 对同一输入正确抛 `invalid_argument`。`pad` 太小（`oh`/`ow` <= 0）同样静默返回 0（实测 `Conv2d(1,1,3,3,0)` + x `[1,1,2,2]` 和 `[1,1,1,1]` 均 err=0）。
- 最小修法：函数入口先做 `if (x.ndim()!=4 || x.dims()[1]!=m.in) throw std::invalid_argument(...)`，再算 `oh/ow` 并 `if (oh<=0||ow<=0) throw`；最省事是入口调用一次 `conv2d_forward(m, x)` 复用现有校验（返回值可丢弃）。注意加行前先做第 13 条的减行，否则会超 280 行。

### 2. CPU 测试没有保护生产实现：改坏 conv 前/反向和 loss 归一化后仍全绿
- 位置：`src/tests/test_gradcheck.cpp:21-59`；`src/ops_cpu.cpp:172-186`（gradcheck 自己重算 dW/db）；`src/conv_cpu.cpp:210-244`（gradcheck 自己重算 conv 解析梯度）、`211`（数值 loss 只用 `conv_forward_f64`，从不调用 `conv2d_forward`）。
- 问题：gradcheck 重写了一套 loss/前向/解析梯度当参考，而不是拿生产函数去比；`gradcheck_linear` 至少用 `linear_forward` 和 `softmax_ce_grad` 产生 logits/dlogits，所以 linear 前向和 softmax grad 有保护；**`linear_backward`、`conv2d_forward`、`conv2d_backward`、`softmax_ce_loss` 的归一化没有任何 CPU 侧断言**。实测变异（在 `/tmp` 副本上改、跑仓库测试）：
  - `linear_backward` 的 `g.dW[...] = acc` 改成 `0`（ops_cpu.cpp:96）：`test_gradcheck` **PASS**，只有 `test_linear_cuda`（需要 GPU 的 parity）红。
  - `conv2d_backward` 的 `g.db[oc] = acc` 改成 `0`（conv_cpu.cpp:161）：`test_gradcheck` 根本不包含 conv，**PASS**；只有 `test_conv_cuda` 红。
  - `softmax_ce_loss` 把 `total / n` 改成 `total`（ops_cpu.cpp:137，loss 从 0.8295 变 1.6591）：`test_gradcheck` 只查 finite/非负，**PASS**；只有 `test_softmax_cuda` parity 能红。
  - `conv2d_forward` 的 `acc = m.b[oc] + 100`（conv_cpu.cpp:83）：`gradcheck_conv2d` 结果仍是 `6.02e-9` **PASS**（它不调用生产前向）。
  - 对照：`linear_forward` 偏置 k=0 加 100（ops_cpu.cpp:67）会让 `test_gradcheck` 红（err 0.68），证明现有机制能抓 linear 前向，抓不到 conv。
- 后果：只要不跑 CUDA parity（无 GPU、或 CI 只跑前 3 个 CPU 测试），conv 前/反向和 loss 归一化就是“零保护”；也违反 doc 11 §5.3“增加至少 1 个能区分改前失败/改后通过的测试”。
- 最小修法：让 gradcheck 的 FP64 参考值保留，但比对对象换成生产函数——`gradcheck_linear` 里同时检查 `linear_backward(m,x,dlogits)` 的 dW/db/dx 与 FP64 解析值（阈值 1e-5）；`gradcheck_conv2d` 里同样检查 `conv2d_forward` 与 `conv2d_backward`；`gradcheck_conv2d` 的调用从 `test_conv_cuda.cpp:117` 移到 CPU 的 `test_gradcheck.cpp`（或两处都调），并给 `softmax_ce_loss` 加固定期望值断言（当前值 0.829538）。

## 应该修

### 3. “label 越界”测试无效，CPU 的 label 检查无人测试
- 位置：`src/tests/test_softmax_cuda.cpp:61-69`；CPU 检查在 `src/ops_cpu.cpp:127-130`、`151-154`；CUDA 检查顺序 `src/softmax_cuda.cu:91`（长度）先于 `:94-95`（范围）。
- 问题：`bad = {2,9}` 只有 2 个元素，而 logits 是 N=6；`check_dims` 先在长度检查抛异常，**范围检查分支从未执行**。实测变异：把 CUDA 的 `label >= c` 改成 `label > c`（放过 `label==C`，会越界读 `row[C]`），`test_softmax_cuda` 仍 **PASS**；把 CPU 两处 label 检查整段删除后，`test_gradcheck` 与 `test_softmax_cuda` 仍 **PASS**（合并变异构建，无任何测试因此变红）。
- 最小修法：用 6 个标签且含一个越界值（如 `{2,0,3,1,4,5}`）分别测试 `softmax_ce_loss`/`softmax_ce_grad` 的 CPU 与 CUDA 入口，并补负 label 用例。另注意 `softmax_ce_loss_f64`（ops_cpu.cpp:37-49）里的 `row[labels[i]]` 自身不查界，目前只因 `softmax_ce_grad` 在 ops_cpu.cpp:174 先被调用而“顺带”安全，重构时要显式校验。

### 4. `Linear`/`Conv2d` 的 W/b 形状不变量没有任何校验，误用即越界读
- 位置：`src/ops_cpu.cpp:58-114`（b 在 67/98-102，W 在 69/108）；`src/conv_cpu.cpp:64-190`（b 在 83，W 在 90-92/178-179）。两个结构体的 `in/out/W/b` 全是 public 字段。
- 问题（均为 ASan 实测 heap-buffer-overflow）：
  - `Linear m; m.in=4; m.out=3; linear_forward(m, x[2,4])`：W 还是默认 1 元素标量，`ops_cpu.cpp:69` 越界读（模型组装时“先填 in/out、后填 W”很容易踩到，HANDOFF 下一步正是模型组装）。
  - `Linear m(4,3); m.b=Tensor::zeros({1}); linear_forward(...)`：`ops_cpu.cpp:67` 越界读。
  - `Conv2d c(1,2,3,3,1); c.W=Tensor::zeros({2}); conv2d_forward(...)`：`conv_cpu.cpp:90-92` 越界读。
  - 若 W 的 numel 正确但布局转置（如 `{in,out}`），则不越界、静默算错。
- 最小修法：`linear_forward/linear_backward` 入口校验 `m.W.numel()==out*in && m.b.numel()==out`（最好连 dims），conv 校验 `m.W.numel()==out*in*kh*kw`，不匹配抛 `invalid_argument`。代价每层一次乘法，可接受。

### 5. 空 batch（N=0）三种行为不一致：CPU 返回 NaN、gradcheck 假通过、CUDA 进程退出
- 位置：`src/ops_cpu.cpp:137`（`total / n`，n=0 得 NaN）、`202`（`std::max(max_err, fabs(NaN))` 返回旧值，NaN 被吞）；`src/conv_cpu.cpp:192-269`（oh=0 或 n=0 时各循环不执行，err=0）；CUDA 启动 `src/linear_cuda.cu:122`、`src/conv_cuda.cu:190-191`、`src/softmax_cuda.cu:114`（grid=0）。
- 问题与场景：
  - `softmax_ce_loss(Tensor::zeros({0,3}), {})` 实测返回 NaN（不抛错）；数据为空或最后一个 batch 为 0 时，训练 loss 静默变 NaN。
  - `gradcheck_linear(m, Tensor::zeros({0,4}), {})` 实测返回 **0**（看起来“梯度完美”）；`gradcheck_conv2d` 在 N=0 或 `oh=0` 时同样返回 0。
  - 同一输入走 CUDA：实测 `CUDA kernel softmax_ce_loss_kernel: invalid configuration argument` 后 `std::exit(EXIT_FAILURE)`，整个进程退出（linear/grad 同理）。CPU/CUDA 语义不一致。
  - 顺带：`softmax_ce_loss` 对 `[1,0]` 的合法 label 报“label 越界”，掩盖真正原因（C=0）。
- 最小修法：`softmax_ce_loss/grad` 与两个 gradcheck 入口先判 `n>0 && c>0`，否则抛 `invalid_argument`；C=0 单独报“C 必须为正”。CUDA 侧在 launch 前对 0 元素直接返回/抛错（`.cu` 不在本次主范围，但接口要一致）。

### 6. 非方核（kh≠kw）零覆盖
- 位置：`src/tests/test_conv_cuda.cpp:66,86,106`（三组配置全是 3x3）；`src/include/uavrgb/conv.hpp:12,19` 明确允许独立的 kh/kw。
- 问题：方核时 `{out,in,kh,kw}` 与 `{out,in,kw,kh}` 的 dims/numel 完全相同，`ki*kw+kj` 与 `kj*kh+ki` 的差异也不会在方核 + 对称权重之外暴露。测试无法发现 kh/kw 顺序混淆；等模型用 3x5 卷积时才静默转置。当前实现**未见错误**（我已用独立参考核对 2x3 核，见下），但这是覆盖缺口。
- 最小修法：在 CPU gradcheck（建议移到 `test_gradcheck.cpp`）和 CUDA parity 各加一组 `kh=2, kw=3, pad=1` 的配置。

### 7. 没有独立的 NumPy/PyTorch 测试级 oracle（doc 04 §6 N2 未落实）
- 位置：`src/tests/`（无任何外部参考）；现有 oracles 只有 FP64 有限差分（同一作者、同一套下标约定）和 CPU/CUDA parity（两套实现同作者、同约定）。
- 问题：共同的约定错误（例如核翻转方向、pad 正负号、W 布局）会同时骗过 gradcheck 与 parity。按 doc 04 §6 N2 本应有独立 oracle。
- 现状核实：我临时用纯 Python 参考（非仓库文件）核对了 pad=1、2x3 非方核的一组 conv 与 linear/softmax，最大绝对差：y `4.6e-8`、dW `1.1e-8`、db `3.0e-8`、dx `1.0e-8`、linear 前反向 `≤1.9e-9`、softmax grad `6.5e-9`、loss `4.5e-9`——**当前数值与布局正确**，缺的是自动化保护。
- 最小修法：加一个小的固定期望值（golden values）测试或 `.venv-tools` 下的 NumPy 对拍脚本，至少覆盖一组 conv（pad=1、非方核）与 softmax/linear；不引入 PyTorch。

## 可以改

### 8. `Tensor::numel()` 无乘法溢出检查
- 位置：`src/tensor.cpp:33-42`。
- 问题：`Tensor t({1LL<<32, 1LL<<32})` 实测 `numel()==0`、`data_` 为空；随后 `t[0]` 直接 SEGV。`from_flat` 对这种 dims + 空 data 也会通过（numel==0）。场景：shape 来自配置/反序列化或某处算错，溢出后得到“2 维但 0 元素”的张量，第一次索引就崩，而不是构造时报错。
- 最小修法：累乘时 `if (d != 0 && n > SIZE_MAX / static_cast<std::size_t>(d)) throw std::length_error(...)`。

### 9. `operator[]` 无任何检查，且允许构造零尺寸张量
- 位置：`src/include/uavrgb/tensor.hpp:24-25`；`src/tensor.cpp:9-17` 允许 `{2,0}`/`{0}`。
- 问题：`Tensor t({2,0}); t[0]` 实测 UBSan “reference binding to null pointer” 后 ASan SEGV。头文件第 12 行注释称默认构造“避免空存储被索引”，但 public 构造函数仍能造出空存储；空 batch 又确实需要 0 维，不能一刀切禁止。
- 最小修法：debug 下 `assert(i < data_.size())`（stdlib 风格），或加 `at()` 并在内部热路径继续用 `[]`；在头文件注明 `[]` 不查界。

### 10. `pad` 无上界，`2*pad` 有符号溢出（UBSan 实测）
- 位置：`src/conv_cpu.cpp:73-74`（forward）、`113-114`（backward）、`201-202`（gradcheck）；CUDA 对应 `conv_cuda.cu:53,82,127,165`。
- 问题：`Conv2d m(1,1,1,1, 1<<30)` 通过构造函数校验（只查 `pad >= 0`），`conv2d_forward` 里实测 UBSan 报 `signed integer overflow: 1073741824 * 2 cannot be represented in type 'int'`，随后得到错误输出尺寸（可能落到负 oh 抛异常，也可能按错误尺寸计算）。
- 最小修法：构造函数限制合理上界（例如 `pad <= max(kh,kw)` 或 `INT_MAX/2`），或输出尺寸一律用 `int64_t` 计算后再范围检查。

### 11. `ActionAdapter::quantize` 的阈值边界与负 eps 未定义、未测试
- 位置：`src/action.cpp:10-16`；文档 `src/include/uavrgb/action.hpp:19`（“低于阈值回退”）。
- 问题：实测 `quantize(0.0f, 0.05f)` 与 `quantize(0.1f, 0.0f)` 都返回 SAFE_NEUTRAL——代码用严格 `>`，而文档写“低于阈值”，恰好等于阈值时语义未固定（疑似，需产品确认）。更明确的是负 eps：`quantize(0.0f, 0.0f, -1.0f, -1.0f)` 实测返回 YAW_RIGHT(3)，零运动也被判成偏航（配置传负阈值即触发）。
- 最小修法：入口校验 `fwd_eps >= 0 && yaw_eps >= 0`（抛 `invalid_argument` 或 clamp）；确认边界后用 `>=` 或改文档，并在 `test_action.cpp` 加相等阈值、自定义 eps、NaN 用例。

### 12. `gradcheck_linear` 对 rank<2 的 x 抛 `std::out_of_range` 而非 `invalid_argument`
- 位置：`src/ops_cpu.cpp:168-170`（直接 `dims().at(0)/.at(1)`，此时尚未调用 `linear_forward` 校验）。
- 问题：实测 `gradcheck_linear(m, Tensor::zeros({4}), {0})` 抛 `std::out_of_range: vector::_M_range_check`；调用方若按其它入口的约定 catch `std::invalid_argument` 会漏掉。

### 13. 重复实现与 280 行预算：conv_cpu.cpp 已到 271/280 行

### 数值结论
- gradcheck 的 `eps=1e-6` **合适**：参数/输入先复制成 double，中心差分全程 FP64；实测 `gradcheck_linear` 最大误差 `2.75e-8`，`gradcheck_conv2d` `6.02e-9`，离 1e-5 门槛有 2-3 个数量级余量。linear 侧解析梯度用的 float dlogits 把误差下限抬到约 3e-8，仍远低于门槛。
- softmax 先减行最大值实现正确；用 ±8 logits 的 parity 测试通过（grad 差 4.7e-10）。
- CPU/CUDA 约定一致：NCHW、stride=1、互相关（不翻核）、W 布局 `[out][in]` / `[out][in][kh][kw]`，pad 公式 `ih=oi-pad+ki`；parity 与独立参考均支持这一点。CPU/CUDA parity 余量：conv dW `1.53e-5` vs 门槛 `1e-4`（约 6.5 倍）、linear 最差 `1.9e-6`。
- 未发现严格别名、迭代器失效、未初始化生产内存问题；`std::vector` 均为深拷贝。

## 结论：

共 14 条：必须修 2 条、应该修 5 条、可以改 7 条。**最严重的是**：(1) `gradcheck_conv2d` 缺输入校验，rank 不足直接堆越界、形状不符假通过；(2) CPU 测试不保护生产 conv 前/反向与 softmax loss 归一化，实测改坏后 CPU 测试全绿，只有需要 GPU 的 parity 会红；(4) `Linear/Conv2d` 的 W/b 形状不变量缺失，模型组装时误填即 ASan 越界读。生产数值本身经独立 NumPy 参考核对是正确的（误差 ≤4.6e-8），问题集中在输入校验与测试有效性；`eps=1e-6` 与 stable softmax 实现没有问题。ASan+UBSan 全部 7 个测试跑通（需 `ASAN_OPTIONS=protect_shadow_gap=0` 才能与 CUDA 共存），未修改仓库源码。
