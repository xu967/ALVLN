## 做了什么

- `sim/tools/nav_cond.py`（新）：纯函数 `heading_code(n, setpoint=0)`（n−H ≥2 → 码 2，≤−2 → 码 3，其余 0，码 1 不用）与 `heading_codes(executed, setpoint=0)`（每步取执行**前**的 n，首帧 n=0）；同一个文件放评测端闸门 `check_student_cond(requested, ckpt, prev_dim)` 与数据集 meta 读取。自检 `python sim/tools/nav_cond.py` 含任务卡的验收例：动作 F L L F R → 码 0 0 0 2 2。
- `tools/preprocess.py`：`--cond {prev-action,heading-code}`，默认 prev-action。heading-code 把码写进侧车 `prev_action` 列，按集从头累计**已执行**动作（含被 `--drop-collision` 丢掉的步，所以丢步不会让后面的码错位），meta 顶层加 `cond: "heading_code.v1"`。带 waypoint 的 episode 在这个选项下直接拒绝（H 未定义）。
- `sim/tools/collect.py`：`--student-cond {prev-action,heading-code}`，默认不变；heading-code 时传给 `student.act()` 的是 `nav_cond.heading_code(net_yaw)`，`net_yaw` 是采集循环里已有的已执行 YAW_LEFT−YAW_RIGHT 计数。行里追加键 `cond_code`（仅 heading-code 时写，0 也写），manifest 里记同名键（仅非默认时写）。仅能和 `--policy student` 同用。
- `sim/tools/collect_parallel.py`（卡面清单之外）：DAgger 流水线经它采集，不转发则 `CFG["student_cond"]` 到不了 `collect.py`；只在非默认时加 `--student-cond`，采集 manifest 同样只在非默认时记。
- `sim/tools/eval_closed_loop.py`：`--student-cond` 透传到 `collect.py`，记入 `eval.json`；起跑前闸门读训练条件：
  - `prev_dim=0` 的 ckpt（图像模型）要求 heading-code → 报错退出；默认值 → 通过且 `eval.json` 无新增键。
  - `prev_dim>0` 的 ckpt：读 ckpt 同目录 `config.json`（没有则读 `<ckpt>.json` 里 `run` 目录的），拿到训练数据集，核对 `dataset_sha256`，再看数据集 meta 的 `cond`：`heading_code.v1` = heading-code，没有该键 = prev-action；与 `--student-cond` 不同 → `p.error` 退出。
  - 拿不到训练条件（没有 config、数据集被换过、标签认不得）→ stderr 警告并把 `student_cond_check`（status `unverified`）写进 `eval.json`，不猜。
- `tools/dagger_gz_pipeline.py`：`CFG["student_cond"]`（默认 prev-action）透传给采集、打包、评测；heading-code 时训练命令追加 `--prev-action`（卡面没写，不加则训出的模型没有条件输入，评测闸门会拒绝）。基线评测（`baselines()`）与教师采集不传该参数。
- 测试：`sim/tools/test_nav_cond.py` 18 例、`sim/tools/test_nav_cond_wiring.py` 23 例（采集单步、采集主循环、`collect_parallel`、评测透传与闸门）、`tools/test_preprocess_cond.py` 9 例（同一批 episode 两种 `--cond` 打包：图像与标签逐字节相同，只有条件列不同）、`tools/test_dagger_gz_pipeline.py` 新增 2 例（共 20 例）、`sim/tools/test_collect.py` 新增 8 项检查（net_yaw −3..3 共 7 项，默认路径 1 项；共 116 项）。
- `tools/DATASET_FORMAT.md`：§1 meta 字段表加 `cond`，§6.2 的 `prev_action` 行写明 heading-code 包里这一列的含义。
- 草稿、先红日志、默认逐位比对脚本与日志：`/root/rivermind-data/uav_rgb/tmp/phase12-cards/w1-9/`；报告 `/root/rivermind-data/uav_rgb/tmp/phase12-cards/reports/w1-9.md`。

## 没做什么

- 没训练、没采集、没起 Gazebo。原因：任务卡「本步不训练」；Gazebo 链路由 E2E-1 的冒烟走一遍。
- 没改 C++（`src/` 0 行）、没改网络结构。原因：任务卡；推理协议里 `prev_dim>0` 时多 1 字节条件已有（`sim/tools/student.py` 与 `src/infer.cpp`）。
- 没改 W1-0 的键与顺序（`dispatch_lag_s` 等）。采集行新键 `cond_code` 追加在行末，只在 heading-code 时出现。
- 没给 `--augment flip` 单独做码对换。原因：训练器的 `flip_side_inputs`（`src/trainer_dev.cpp`）对 prev-action 值 2↔3 互换，码 2/3 与 YAW_LEFT/YAW_RIGHT 的数值相同，同一条规则已覆盖；该路径的数值测试没写，标「未核实」。
- 没对 `dagger_gz_pipeline.py` 的 `round0_ckpt` 做条件校验（只在 `CFG` 注释里写明必须同条件训练）。原因：任务卡没要求；基线评测不传 `--student-cond`，heading-code 的 round0 ckpt 会被评测闸门当作不一致拒绝，错误信息指向原因。流水线整条没跑，该行为只由 dry-run 测试覆盖。
- 没动 `progress.md`、`CLAUDE.md`，没合并、没推送。原因：交办。

## 待确认

- 闸门在 `prev_dim>0` 且拿不到训练配置时只警告不拒绝（任务卡「拿不到则警告并写入 eval.json，不猜」）。已有的 prev-action 老 ckpt 若旁边没有 `config.json`，评测会多出这条警告和 `eval.json` 键；`prev_dim=0` 的 ckpt 不受影响。
- `check_student_cond` 对非整数的 `prev_dim`（测试里的 `Mock`）按 0 处理，目的是不改别人的测试；真实 `Student.prev_dim` 是整数。
- 采集行的 `cond_code` 是卡面之外的审计键，E2E-1 冒烟用它核对「送进推理的码 = `nav_cond`」。

## 风险与遗留

- 默认路径不变靠两层证据：单元测试里的「默认下传给学生的仍是 `prev_executed`、行里没有 `cond_code`、manifest 没有新键」，以及真实 6 集上旧新打包逐位相同。`eval_closed_loop.py` 默认路径只有测试覆盖（`Mock` 学生），没有整条 Gazebo 评测的对拍。
- heading-code 的 `net_yaw` 由采集/评测进程自己累计，不读飞控估计。真机上对应「飞控偏航估计相对起飞航向的差」，这条对应关系没有验证。
- `--cond heading-code` 的包只适用于 H 恒为 0 的任务（柱阵、长课程）；waypoint 任务被拒绝，不是做不到而是 H 的定义没给。
