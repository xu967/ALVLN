## 4. P0：不解决就无法形成有效论文结论

### P0-1｜研究空间已被两篇 2026 论文正面覆盖，而你的方案零引用

这是本轮最重要的发现。你只在 `(2).md` 的第 4 问里点了 LightVLN 和 AirAnchor 的名字，`V7_1_RESEARCH_PLAN.md` 正文里**一次都没有出现**。我核实了这两篇：

**LightVLN**（arXiv:2610.05024，2026-10-06，HKUST-GZ）
- "轻量级、历史感知的空中 VLN 框架"；**每个历史帧压缩成一个 token**；**history- and instruction-conditioned 局部聚合，把当前观测从 256 个视觉 token 压到 32 个**；16 帧历史下观测 token 总数 ≤48
- OpenFly Test-Seen 50.93% / Test-Unseen 36.14%；**AerialVLN-S Val-Seen SR 25.83%**
- DJI M350 + Jetson Orin NX 16 GB，**实测 14.61 Hz 推理、11.13 Hz 端到端决策**

对照你的 §7.3："记忆：小 GRU 或显式 gated state"+"跨模态：保留少量空间 token，用当前指令相关特征对照全局池化基线"——**这就是 LightVLN 的 compact memory + instruction-conditioned local aggregation，一字不差**。而"板端 Hz 实测 + 机载部署"这条原本属于你的差异化故事，它已经做了。

**AirAnchor**（arXiv:2609.08442，2026-09-08）
- 零样本 AerialVLN-S；三件套：Query-Driven Spatial Anchor Grounding / Persistent Object Spatial Memory（SOKB）/ Spatially-Informed Navigation Agent
- **Progress Reflection**：原文写"对导航进度的可靠推理往往取决于空间关系的变化，而不只是文本或视觉语义——例如判断无人机是否已经**经过**或**飞越**了某个地标"，输出 `(γ, b, π)` ＝ 进度评估、子任务完成二值、下一步计划

对照你的核心命题"通过视觉证据与指令进度协同的紧凑状态，改善动作与终止判断"——**这就是 AirAnchor 的 Progress Reflection 加空间锚点记忆**。

**判定：如果 ECPT 按现有描述实现，与 AirAnchor（进度反思 + 地标持久记忆）+ LightVLN（紧凑历史记忆 + 指令条件局部聚合）的机制重合度约 70%。** 审稿人会把这条写在拒稿第一段，而且他有现成的两句摘要可以引用。

**最小改动（三条路，选一条，别都做）**：
1. **收缩到"容量下界"这个角度**：LightVLN 用 0.5B 语言骨干，AirAnchor 用 Qwen3.6-Plus 在线 API。**没有人回答"当语言骨干只有 20 万参数、总模型 1 MB 时，空中 VLN 还剩多少能力"**。这是一个它们结构上不会碰的问题（碰了就没法用 MLLM），而你有 SG2002 这个硬约束替你背书。做"容量-性能曲线"（0.1M / 0.3M / 1M / 3M 参数 × 同样方法），结论本身就是贡献，且不需要打赢 SOTA。
2. **收缩到"终止/STOP 校准"这个单点**：AirAnchor 的 Progress Reflection 是 MLLM 输出的二值 `b`，没有校准、没有阈值分析、没有早停/晚停的错误分解。**用一个小模型把 STOP 做成"有标定的风险决策"**（期望距离回归 + 阈值扫描 + 早停/晚停分型），是一个更窄但更硬、可完全量化的贡献。你 §15.3 已经在朝这个方向想，把它提为主贡献。
3. **收缩到"无地图 vs 有地图"的受控对照**：AirAnchor 与 LookasideVLN 都依赖持久地标库/空间锚点。**在只有单目 RGB、无任何先验地图、无在线建图的条件下，性能损失多少？** 这是一个干净的 ablation 问题，负结果也有价值。

> **放弃条件**：如果 3 周内无法写出一页 ECPT 规格、且无法说出它比 AirAnchor 的 Progress Reflection 多做了哪一件可测的事——**删掉 ECPT 这个名字**，直接以"容量-性能研究 + STOP 校准 + 板端实测"立题。名字不重要，能测才重要。

**而 AirAnchor 的 Table 1 给出了可用作对照的数字**（我从 arXiv HTML 抄录；该表在 HTML→文本转换中有列错位风险，**引用前请回原文核对**）：AerialVLN-S 学习型基线 SR ≈ Seq2Seq 4.8、CMA 3.0、LAG 7.2（2023）；零样本 AirAnchor 9.6。

把这组数字代进功效公式（α=0.05 双侧，power=0.8）：

| 基线 SR | 检出 +3pp | +5pp | +8pp | +10pp |
|---|---:|---:|---:|---:|
| 5% | 1,247 | 435 | 176 | 113 |
| 7% | 1,655 | 597 | 244 | 158 |
| 10% | 1,774 | 686 | 295 | 199 |
| 15% | 2,402 | 906 | 377 | 250 |

而 AerialVLN-S 的 val_seen = 333、val_unseen = 531（**仅 5 个未见场景**）。

**两个硬结论**：
- 你在 SR≈5–10% 这个区间，**531 条只能分辨约 +8–10pp**。任何"ECPT 带来 +3pp"的结论，在算术上不可证。
- **实操含义很直接：一个 1M 参数的学生，如果 SR 拿不到 ~8%，就不如 2023 年的 LAG（7.2%）。** 这是你必须先跨越的门槛，比"比 AirAnchor 好"实际得多。

**最小改动**：
- 目标写成"**先超过 LAG 7.2%，再逼近 AirAnchor 9.6%**"，写进 METHOD gate 的 PASS 标准；
- 预先声明"**SR 差异 <5pp 一律写成未观察到可分辨差异**"；
- 报 **per-scene（5 个场景各自 SR）+ 场景级 bootstrap CI + ≥5 seeds**；
- 因为你还要自建 Gazebo 数据（可以造得很大），**把"大样本"能力用在自己数据上做主消融，把 AerialVLN-S 只用于"对外可比"**——这是唯一能同时满足"统计功效"和"外部可比"的分工。

UART 协议（MAGIC/VERSION/SEQ/TTL/CRC/ACK/EXEC_DONE/REJECTED）、飞控唯一仲裁、无桨台架 10 项故障注入——这是全篇最扎实的工程内容。但 HIL gate 在 §14 表里排第 15 位，前面有 14 个 gate。

### P1-5｜STOP 的问题问得好，但"剔除阈值调参污染"没有方法

你在第 5 问里问得准（"STOP 单独 head 在相同数据、容量、计算下是否优于仅 8-way softmax？如何剔除阈值调参污染？"）。这确实是这个方向最容易做假的地方。但方案里没有给出解法。

## 6. P2：代码级缺陷，每条我都复现过

以下 5 条我都有可执行复现，不是推测。

### P2-1｜嵌套 NaN 穿透过滤，并被错误地报成 404

`metrics_for` 的有限性检查只查顶层：
```python
if any(isinstance(v, float) and not math.isfinite(v) for v in event.values()):
```
嵌套结构（`{"event":"train_step","metrics":{"loss":NaN}}`）通过检查 → 进入 `rows` → 序列化时 `json.dumps(..., allow_nan=False)` 抛 `ValueError` → 被 `except ValueError` 捕获 → **返回 404，错误信息是英文 `Out of range float values are not JSON compliant: nan`**。

我实测的输出：
```
只要 event 是 str 就通过过滤, events = 1  warnings = []
>>> json.dumps 抛 ValueError -> Handler 里会被 except ValueError 捕获 -> send_error(404)
```

三重问题：① `(2).md` 的 C06 声称"拒绝 NaN"，实际只拒顶层；② 404 是"资源不存在"的语义，数据格式错误应是 5xx 或降级为 warning；③ 用户看到英文异常而无 `LOG_NONFINITE` 这样的机器可读码，与你的错误码体系冲突。

**修法**：递归检查 + 把 `json.dumps` 的 `ValueError` 与 `RUN_NOT_FOUND` 分开捕获（前者给 `LOG_NONFINITE`/500，后者给 404）。

### P2-2｜两个 run_id 校验器不一致，训练 run 会静默消失

```python
# launcher.py:46
if not run_id.replace('_', '').isalnum() or len(run_id) > 70:   # '跑次_001'.isalnum() == True
# dashboard.py:23
RUN_ID = re.compile(r'^[A-Za-z0-9_]{1,70}$')                     # '跑次_001' 不匹配
```
实测：`跑次_001` → launcher 允许建目录 → dashboard 的 `runs_list()` 过滤掉 → 看板看不到 → `/api/metrics?run=跑次_001` 返回 404。

这是最坏的一类 bug：**训练跑了、日志写了、界面上永远没有。** 对一个"绝不伪造指标"的项目，静默丢数据同样是可信度事故。

**修法**：把 `RUN_ID` 抽到一个共用模块，两处引用同一常量；launcher 侧改成 `RUN_ID.fullmatch(...)`。

### P2-3｜`forest` 与 `mixed` 是同一个生成器

`create_obstacles` 只有 `corridor` / `columns` / `else` 三个分支，`forest` 和 `mixed` 都落到 `else`。实测 seed=42、count=40 时两者坐标列表逐元素相同。

**修法**：要么给 `mixed` 真正的混合逻辑（例如按比例混入 corridor 的窄通道段），要么删掉这个 preset。**留着它会让"四档难度"这个说法不成立**——而难度分档是你 §6.4 的核心设计。

### P2-4｜`runs_list()` 上限 80，超出的旧 run 永久不可见

实测：建 85 个 run，`runs_list()` 只返回 80，最老的 5 个无法通过任何 API 访问（`metrics_for` 先查 `name not in runs_list()`）。

**修法**：`runs_list()` 不加截断（只返回名字，成本极低），在渲染层截断。

### P2-5｜`.gitignore` 排除 `artifacts/`，但 sim 测试依赖 `artifacts/scenes/forest_42.sdf`

`.gitignore` 第 1 行 `artifacts/`；`sim/tests/test_v7_contract.py` 硬编码读 `artifacts/scenes/forest_42.sdf`。

后果：fresh clone → 该文件不存在 → `sim_preflight` 返回 `GZ_WORLD_NOT_FOUND`（exit 4）而不是 `GZ_MOTOR_MODEL_MISSING` → 断言失败。**测试在干净仓库上必挂**，且违反你自己 CODE_RULES 第 3 条（"场景只能进 artifacts/"）。

**修法**：把测试夹具 SDF 移出 `artifacts/`（如 `sim/tests/fixtures/static_no_motor.sdf`，明确标注为夹具而非场景）。

### P2-6｜文档承诺的 CLI 有两条不存在

`V7_1_RESEARCH_PLAN.md` §11 列了 `./run.sh board doctor` 和 `./run.sh uart dry-run`；`launcher.py` 的 `choices` 只有 `doctor/scene/dashboard/ui/train/eval`。实测：
```
launcher.py: error: argument command: invalid choice: 'board'  exit=2
```
exit 2 是 argparse 的参数错误，不是你的 `FEATURE_NOT_IMPLEMENTED`（应为 3）。**机器可读的错误码体系在这里断了一次。**

**修法**：把 `board`/`uart` 加进 choices 并统一返回 3 + `FEATURE_NOT_IMPLEMENTED`。

### P2-7｜`sim doctor` 打印 `[BLOCKED]` 却返回 0

```python
print("[BLOCKED][GZ_PHYSICS_NOT_VERIFIED] ...")
return 0
```
这条直接违反你 CODE_RULES 第 9 条（"未实现某功能时必须非零退出"）。CI 会把 exit 0 当成功，而人眼看到 BLOCKED——**两条通道互相矛盾**，恰恰是这套体系最想消灭的东西。

**修法**：找到 gz 但物理未验证 → 返回非 0（建议 6，含义"部分可用但功能未验收"），或拆成 `doctor`（只看依赖）+ `verify`（必须实测）。

### P2-8｜`scene_tool` 用文本模式写 SDF，而哈希基于 LF 字符串

```python
world_path.write_text(sdf, encoding='utf-8')                      # Windows 上 \n → \r\n
'sha256': hashlib.sha256(sdf.encode()).hexdigest()                # 哈希基于 LF 版本
```
在 Windows 上，文件字节 ≠ 哈希对应字节 → `test_scene_deterministic_and_well_formed` 失败（我在本地就挂在这）。Ubuntu 上正常，所以你的 13 PASS 是真的。

但这不只是平台问题：**"内容哈希"这个契约没有绑定"写入路径"**。将来任何人用不同的写入方式生成场景，哈希就会失真，而哈希是你整个 `manifests/` 可复现体系的地基。

**修法**：`world_path.write_bytes(sdf.encode('utf-8'))`，哈希与其他写入共用同一条 `bytes` 路径。

### P2-9｜单个坏 run 会让整站显示"接口连接异常"

`refresh()` 里对选中 run 的 `request('/api/metrics?run=...')` 若 404（例如 P2-1/P2-2 造成），异常被外层 `catch` 捕获 → `setText('health','接口连接异常')` → **整个看板显示离线**，而实际上其它端点都正常。

**修法**：metrics 的失败单独 catch，显示"该 run 指标不可读"，不污染全局健康状态。

### P2-10｜其他小事

- `log_message` 打到 stdout，长期运行的管道会堵；应写文件或按级别抑制。
- `ThreadingHTTPServer` 无 `timeout`，慢连接会占线程（本地只读，风险低，但可加 `daemon_threads = True`）。
- `TrainingMonitor` 无锁；若将来多线程写 metrics 会交错。当前单线程，标注为已知限制即可。
- `training_monitor.hpp` 的 `Status()` 不写 `severity` 字段，而 HTML 的"警告"筛选依赖 `severity`/`code`；建议补 `severity`。

## 11. 结论

**保留这个项目的三个理由**（它们是真的）：
1. 你的**证据纪律**（分级标注、拒造假指标、gate 不可传递）在同类工作中属于前 5%，这套东西本身就是可发表的方法论。
2. 你的**安全论证**（STOP 语义、飞控唯一仲裁、定高缺口识别）比多数无人机论文更严谨。
3. **"1 MB 权重能不能做空中 VLN"这个问题是真的没人回答**——LightVLN 用 0.5B，AirAnchor 用云端 MLLM，你在物理上不可能与它们同赛道。这是你的位置。

**必须改的三件事**：
1. **把 ECPT 定义出来，或者删掉这个名字。** 四个月、四版、一个缩写、零定义——这是研究工作的红灯，不是文档工作的黄灯。
2. **物理轨二选一。** 用 Gazebo 自带控制器把语言闭环做成（快），或只做 CF 姿态级验证（真），不要两者都要。
3. **本周产出一个 SR 数字。** 哪怕它只有 3%、只有 333 条 episode、用的是 PyTorch——一个真数字胜过 973 行文档。

**最后一句**：V7.1 的文档质量足以让我认真评审，而它的代码量不足以让我评审研究。这两件事的落差，就是你现在唯一要解决的问题。你已经证明了自己会写"不许自欺"的规则；下一步要证明的是，**你会遵守它——从今天开始，先跑，再写。**
