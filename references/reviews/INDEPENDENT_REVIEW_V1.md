## 3. P0 阻断项

### P0-1　关键路径倒置：7 个非研究工程门禁挡在研究结果之前，而唯一的外部标尺被自己延后

**证据**

- `[实读]` 评审包 §3 X11：「AerialVLN-S 官方仿真器 + 5090 兼容性 —— **延后官方 benchmark**，不虚构成绩」。
- `[实读]` 主方案 §17 第一批 10 项任务中，第 1–7 项（CF 硬件矩阵、Gazebo 官方 demo、相机、世界合成、手动动力环、CF SIL、语言专家）**全部是工程**，第 8 项才出现自研训练，第 9 项才是主方法。
- `[实测]` 当前 `.cc/.cu/.cpp` 实际数量 = **0**。
- `[外部]` E4：外部标尺在 3 周前刚刚被显著抬高。

**为什么这是 P0 而不是「稳扎稳打」**

因为两条轨道的**收益结构不对称**：

- 离散轨（AerialVLN-S）一旦跑通，立刻同时得到：外部可比的 SR/OSR/NE/SDTW、**人类标注好的 25,338 条指令**（不用自己写 task_generator）、官方 split、现成 evaluator。也就是说，你们 §17 里的任务 4（世界合成）与任务 7（语言专家）在离散轨上**已经由 AerialVLN 作者替你们完成了**。
- 物理轨（Gazebo）跑通后得到的是「能出图的物理闭环」，它**本身不构成论文结论**，只是让后续实验更可信。

现在的选择是：**先做 7 个工程任务去换取一个没有外部标尺的自建环境，还是先花 1–2 天验证那个有外部标尺的环境能不能用。** 前者把 7 项工程变成了研究的 precondition；后者最多损失 2 天。

**争议 / 可能推翻我的反例**

如果 AerialVLN 官方仿真器在 RTX 5090 上**根本跑不起来**（UE4 二进制 + 新驱动 + 35GB + AirSim 版本耦合），那么"先 AerialVLN"就是一条死路，我的排序建议就错了。

**所以真正该做的第一步不是选路线，而是做这个判定实验**：

> 在 5090 主机上花 1–2 天，按官方 README 装环境，跑通 10 条 episode 的闭环。**这个实验的输出只有两个值：能跑 / 不能跑**，但它决定了后面半年的顺序。

**最小改动（可分支、可测试、可回滚）**

1. 新增一个 1–2 天的一次性探针任务 `PROBE-AERIALVLN`，产出只有：能否跑通 10 条 episode、单帧渲染耗时、原生渲染分辨率、同 seed 两次渲染是否逐字节一致。
2. 若**能跑** → 离散轨优先：先出 AerialVLN-S 的 RGB-only 基线数字，物理轨并行但不阻塞。
3. 若**不能跑** → 才自建 Gazebo 物理轨，且**此时必须执行 P0-2**（用 PX4 gz_x500 起步）。
4. 无论哪种，X11 的状态都要从「延后」改成「已判定：可/不可，日期 + 证据」。

**放弃条件**

若 AerialVLN 不可用、且自建 Gazebo 在 5090 上 Ogre2 渲染也不可用（X01），则立刻停止物理轨，退回纯离散/纯离线数据轨道，并把项目目标从「物理闭环导航」下调为「离散基准 + 板端延迟测量」。

**改进后实验**

- 固定 split（AerialVLN-S 官方 val_unseen，或自建集中按功效确定的 held-out 集）、固定 3–5 seed、student 合法输入仅为 RGB + 完整指令 + 历史动作 + 循环状态。
- 统计单元 = **轨迹**（不是指令、不是帧）；核心指标顺序 = **SDTW / NE / OSR 优先，SR 次之且必带 CI**。

### P0-2　车辆选型与研究问题过早耦合：CF-Drone SIL 被放在了研究门禁上

**证据**

- `[实读]` 门禁表：CF0（CFMath 黄金对拍）、CF1（CF-Core SIL）、CF2（高度能力/受控速度）位于 DATA0 与 TRAIN 之前。
- `[实读]` §17 任务 6 是 Data/Train 之前必须完成的。
- `[外部]` E6：独立来源确认该机型无 GPS/光流/VIO，「厘米级定位」属不推荐场景。

**判断 `[判断]`**

CF-Drone SIL 解决的是「**这个特定 118 mm 机体的控制律能否在环内复现**」，这是一个**部署移植问题**。而研究问题 RQ（单目 RGB + 长指令 + 低算力下如何改进动作与终止）**与机体型号无关**——只要是一个物理可行的四旋翼 + 前视 RGB 即可。

把 CF SIL 放在 DATA0 之前，等于让研究命题等待一个硬件参数标定工作（§4.5 列出的 m / Ixx,Iyy,Izz / 机臂长 / 重心 / 旋向 / k_f / k_m / 死区 / 响应时间常数，目前**全部未测量**）。

**额外的隐藏成本：X3 与 118 mm 是两个物理尺度。**

`[外部]` E2 显示官方示例用的是 X3（`motorConstant 8.54858e-06`、`maxRotVelocity 800`，属 0.5–1 kg 级）。而 CF 是 118 mm 微型机，动力学时间常数通常快 5–10 倍。因此**用 X3 生成数据、在 118 mm 上部署，会在视觉 sim2real 之外再叠加一个动力学 sim2real 缺口**。方案 §4.5 已经警告「不得把 X3 的 m/kf 写进真实 118mm CF 配置」✓ 这是对的，但方案没有说明**训练数据该用哪一套参数生成**，以及这个落差要不要作为显式实验报告。

**争议 / 可能推翻我的反例**

若项目的最高优先级是「必须复用并验证 CF-Drone 原始控制律」本身（例如研究问题之一就是"Arduino 飞控代码的可移植性"），那 CF SIL 必须在门禁内。但那样的话，研究问题就不该写成 §0.1 的 RQ，两者表述必须统一。

**最小改动**

1. 把 GZ0–GZ3 的**入门载体换成 PX4 官方 `gz_x500`**（方案 §16.3 第 5 条已经引用了它，§2.1 也正确地指出"不能把 PX4 闭环成绩写成已验证 CF-Drone"）。用它把「image → action → next image」打通，预计以周计。
2. CF0/CF1/CF2 降级为 **独立的移植支线**，不再作为 DATA0 的前置。论文中按方案自己的规矩声明：动力学部分用的是 X3/gz_x500，CF 控制律未经实机验证。
3. 明确写定：**训练数据用哪一套车辆参数生成**；若用 X3 而部署在 118 mm，就把「X3→CF 动力学迁移」列为一条显式实验与显式限制，不藏起来。

**放弃条件**

若 CF 实机参数（质量、惯量、k_f/k_m、旋向、响应时间）在合理时间内无法测量，则永久使用公开/官方车辆参数生成数据，并在论文限制节写明「本工作的动力学模型不对应最终部署机体」。

**改进后实验**

同车辆参数、同控制器、同场景集下，只切换策略 A/B，用**同一批 episode 配对**比较（见 P0-4）。

- 对照主方案 §6.2 的任务 YAML：`subgoals_gt` 里写的是 `blue_pillar_1 / yellow_gate_2 / red_marker_3`，§4.3 也要求「同一场景目标地标必须具有不同的材质/颜色/空间拓扑」。

**即：§6.2 的指令模板在当前唯一存在的场景生成器上无法实例化。** 现在能生成的只有「棕色圆柱阵 + 一个红球」，可支撑的指令上限是「朝红球飞然后停下」，也就是 §6.4 的 S0 都不到 S1。

**争议 / 可能推翻我的反例**

若语言任务被有意简化为「只依赖目标球 + 障碍布局，不做地标指称」（即放弃 pass-the-blue-pillar / turn-at-the-yellow-gate 这类指令），则本条降级为 P2。但那样 §6.2 的 YAML 与 §6.4 的 S1–S3 就必须改写，不能两边都留着。

**最小改动（约 60–80 行，可单独分支）**

1. 给障碍物加语义类与颜色：`class ∈ {pillar, gate, marker}`，每类绑定唯一且可区分的 `<diffuse>`，写进 scene manifest。
2. 生成后加一次可解性检查：在 2D 占用网格上做一次 A*（或简化为连通性 + 最小间隙检查），失败则有限次重采样，超出上限记 `SCENE_UNSOLVABLE` 并落盘，**不静默丢弃**。
3. 增加 `difficulty ∈ {S0,S1,S2,S3}` 参数，让障碍密度/地标数量/光照扰动按档位变化，四档都要有可生成的实例。
4. 补测试：断言 S1 场景至少含 2 个不同颜色的地标；构造一个无解场景，断言返回 `SCENE_UNSOLVABLE`。

**放弃条件**

**改进后实验**

## 4. P1 风险项

### P1-1　`[实测]` 场景确定性哈希在跨平台下失效

**证据**

```python
# tools/scene_tool.py:92  文本模式写盘（Windows 下 \n → \r\n）
world_path.write_text(sdf, encoding='utf-8')
# tools/scene_tool.py:96  却对内存中的 LF 字符串取哈希
'sha256': hashlib.sha256(sdf.encode()).hexdigest()
```

我在 Windows 上实测（`[实测]`）：

```
regen file bytes sha256 : ab3d28110cf95d68e5e22a02cc604f5481a338105db41afdeda55fad6a7470be
regen manifest  sha256  : 5d15f5abfd8074f183496a4c6e0e15bdd3bee45e268c32a829db21633823dbe4
regen file contains CRLF: True | CR count: 36 | LF count: 36
MATCH: False
# 把 CRLF 还原成 LF 后哈希 = 5d15f5ab... = manifest 值，验证根因确为换行翻译
```

后果链：该用例在 Linux 通过 → 在 Windows / 任何开启 `core.autocrlf` 的检出 / 任何跨机搬运场景时失败 → 最常见的人类反应是"这个测试太脆弱，先跳过"→ **整个 `manifest + sha256` 数据合同被架空**。而这个合同是方案 §12.3 与 §6.5 的复现基础。

**最小改动（3 行）**

```python
data = sdf.encode('utf-8')
world_path.write_bytes(data)          # 或 write_text(sdf, encoding='utf-8', newline='')
... 'sha256': hashlib.sha256(data).hexdigest()
```

**反例**：若团队永远只在单一 Linux 容器里生成并校验场景，这条永不触发。但数据合同存在的意义就是跨机可验证，所以仍然要修。

**复现门禁**：加一条测试，在生成后断言 `read_bytes()` 的哈希 == manifest 哈希（现在这条测试**确实存在但只比较了内存串**——测试本身也应当改为读回字节再比）。

## 5. 关于"研究发表创新性"的正面建议（对应 A 项 4 分）

这不是批评，是把 4 分往上推的具体路径。

**当前创新性的三个支撑点及其强度**

| 支撑点 | 强度 | 说明 |
|---|---|---|
| 「约 1M 参数、1 TOPS/256MB 的闭环空中 VLN」 | **强** | 这是真实生态位；LightVLN 在 0.5B/Orin NX 档，差约 3 个数量级 |
| 「ECPT 证据校准进度记忆 + 独立 STOP」 | **弱** | 与 Ma et al. 2019（progress monitor）、AirAnchor 2026（progress reflection + subtask）、NavHarness 2026（progress assessment）、QAD 2026（query evidence + token-adaptive KD）四条线重叠 |
| 「C++/CUDA 自研训练器」 | **中，但不是科学贡献** | 是工程量，审稿会认可"可复现/可部署"，不会认可"新方法" |

**建议把主 claim 重写为一句可证伪的话**（替换现有 §16.1）：

> **W1（工作假设）**：在 1 TOPS INT8 / 256MB、静态 shape 的约束下，把"语言进度"作为**同一个瓶颈向量**同时驱动「当前的证据选择」与「终止决策」，能在**等容量、等数据、等种子**的配对消融中，比（a）普通 GRU 进度记忆、（b）8 路 softmax 含 STOP、（c）无进度纯 BC，三个基线各自产生可测的独立收益。

三个基线的存在，就是这条 claim 的证伪装置。若三个都测不出，删掉 ECPT（方案 §16.2 已有这条，✓ 予以肯定）。

**并向 AerialVLN 之外单独加一条**：把 P0-4 的"完美配对评测"作为**方法论贡献**写进论文。这是自建仿真真正值钱的东西，比多一个模块更值得写。

## 9. 最后：三条我可能被推翻的判断，以及怎么推翻

评审包要求"至少写出一个可能推翻评审者自身观点的实验"。我给出三个，并按重要性排序：

1. **推翻 P0-1（轨道顺序）的实验**：在 5090 上按官方 README 装 AerialVLN 并跑通 10 条闭环 episode。若成功，我的"先离散"排序成立；**若失败（且 Ogre2 渲染也失败），我的排序建议就是错的，应立刻转为"最小可行物理轨 + 降低对外比较的野心"**。这是最便宜、最该第一个做的实验。
2. **推翻 P0-3（数据链无法实例化）的实验**：用现有 `scene_tool` 生成 S1 场景，检查它能否产出 §6.2 YAML 里的 `blue_pillar_1 / yellow_gate_2`。若能（说明我漏看了颜色逻辑），本条撤回；**我核查的结论是不能——所有障碍共用 `.42 .36 .27 1`**。
3. **推翻 P1-1（哈希缺陷）的实验**：在纯 Linux 容器里跨两台机器生成并校验同一 seed 的场景。若通过，说明跨机可复现成立，本条降级为 P2；**但我在 Windows 上的实测结果已确证换行翻译会导致哈希失配**——修它只需要 3 行，所以即便降级也建议改。

## 10. 总评

**V7.1 是我在同类方案里见过的最不愿意自我欺骗的一版。**

它的两个品质是真实的：一是对 CF-Drone 能力的审计（§1.1–1.3）——我独立查证后确认其结论站得住（该机型确实无位置/速度/高度传感器）；二是它把"不能把工具存在当成功能通过"写成了代码（五级状态、`no_fake_metrics`、断言无伪造指标的测试）。这两件事加起来的分量，超过多数已经跑出数字的项目。

但它现在有一个新的、比"方法不够新颖"更迫切的问题：

> **它把 7 个工程门禁排在了研究结果之前，同时把唯一的外部标尺延后了；而支撑这些门禁的代码一个字节都还没有。**

治理文本 1,562 行，真实代码 691 行，`code/src` + `code/cuda` + `sim/src` 实际源文件 **0 个**，占位目录 24 个。这个比例不会随着再写一份规则而改善。

**所以我的建议不是"再想清楚一点"，而是：立刻去做那个 1–2 天的 AerialVLN 判定实验，然后根据结果砍掉一半的门禁。**

砍掉门禁不等于降低标准。恰恰相反——**你们已经有足够多的标准了，现在缺的是第一个能被这些标准检验的真实数字。**
